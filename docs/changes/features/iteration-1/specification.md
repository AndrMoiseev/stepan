# Stepan: спецификация итерации 1

Статус: черновик

Итерация: 1 — интерактивная спецификация

## 1. Цель

Реализовать первый пользовательский вертикальный срез Stepan: разработчик
запускает интерактивный режим, выбирает flow работы с идеей и в одной сессии
доводит её до утверждённой спецификации. Stepan управляет диалогом, а
содержательную работу делегирует Codex.

Результат итерации — сохранённая в рабочем дереве спецификация. Планирование,
реализация, проверки и Git commit в этот срез не входят.

## 2. Пользовательские истории

### US-1. Запустить flow работы с идеей

Как разработчик, я хочу после запуска Stepan попасть в интерактивный режим без
автоматического запуска какого-либо flow, чтобы в будущем выбирать между
несколькими flow.

Flow работы с идеей запускается командой `/idea [<idea brief>]`. Если brief
передан в команде, Stepan сразу начинает его уточнение. Если brief отсутствует,
Stepan просит ввести его следующим сообщением.

### US-2. Уточнить требования

Как разработчик, я хочу отвечать на уточняющие вопросы по одному, пока Codex не
решит, что информации достаточно для цельного первого черновика.

### US-3. Получить черновик спецификации

Как разработчик, я хочу получить путь к созданному файлу спецификации, чтобы
прочитать его обычными средствами рабочего окружения.

Первый черновик создаётся только после завершения первоначального уточнения, а
не обновляется после каждого ответа.

### US-4. Обсудить и изменить черновик

Как разработчик, я хочу после создания черновика выбрать продолжение диалога и
явно указать, задаю ли я вопрос по спецификации или предлагаю изменение.

Вопрос не должен менять спецификацию. Запрос изменения может обновить файл. В
этой итерации Stepan показывает разные действия в интерфейсе, но не обязан
технически доказывать отсутствие изменения файла после вопроса.

### US-5. Утвердить спецификацию

Как разработчик, я хочу явно утвердить спецификацию специальной командой
`/approve`, чтобы завершить flow без неявного принятия результата Codex и
вернуться в основной интерактивный режим.

### US-6. Завершить Stepan

Как разработчик, я хочу завершить интерактивный режим сочетанием `Ctrl+C` из
любого состояния.

## 3. Границы

### Входит в итерацию

- интерактивный ввод первоначальной идеи;
- запуск без автоматически выбранного flow;
- запуск flow командой `/idea [<idea brief>]`;
- отдельный запрос brief, если команда `/idea` вызвана без аргумента;
- делегирование содержательной работы Codex;
- уточняющие вопросы строго по одному;
- создание первого черновика после завершения уточнения;
- сохранение спецификации в `docs/specs/<spec-id>/`, где `<spec-id>`
  формируется автоматически из названия задачи;
- обязательный `docs/specs/<spec-id>/specification.md` как точка входа и
  необязательные дополнительные файлы рядом;
- отказ с понятной ошибкой, если целевой каталог уже существует;
- вывод пользователю пути к файлу вместо полного текста спецификации;
- явный выбор после создания черновика: `/approve`, вопрос или предложение
  изменения;
- обновление файла по результатам диалога;
- завершение flow после `/approve` с возвратом в основной интерактивный режим;
- завершение Stepan по `Ctrl+C` из любого состояния, без дополнительного
  подтверждения.

### Не входит в итерацию

- обязательный шаблон или схема содержимого создаваемой спецификации;
- проверка наличия в ней фиксированного набора разделов;
- план реализации;
- изменение кода по созданной спецификации;
- проверки и независимая верификация реализации;
- создание Git commit;
- сохранение состояния диалога и продолжение после перезапуска;
- восстановление оборванной сессии;
- автоматическое удаление неутверждённого черновика;
- полный workflow specification-driven development.

Каждый запуск начинается с чистого диалога. Если пользователь завершил сессию
без `/approve`, уже созданный файл остаётся в рабочем дереве; Stepan не
возобновляет его и не удаляет.

## 4. Критерии приёмки

1. После запуска Stepan ожидает команду пользователя и не запускает flow
   автоматически.
2. `/idea <idea brief>` запускает flow с переданным brief без дополнительного
   запроса brief.
3. После `/idea` без аргумента Stepan просит brief и использует следующее
   сообщение пользователя как его значение.
4. Пользователь проходит flow, не открывая Codex CLI самостоятельно.
5. Пока данных недостаточно, Stepan показывает ровно один вопрос Codex и
   передаёт ответ пользователя в ту же сессию уточнения.
6. До решения Codex о готовности первого черновика файл спецификации не
   создаётся.
7. После готовности черновика существует
   `docs/specs/<spec-id>/specification.md`; дополнительные файлы могут находиться
   в том же каталоге. Stepan показывает пользователю путь к
   `specification.md`.
8. Если целевой каталог уже существует, Stepan сообщает об ошибке и не изменяет
   его.
9. После создания черновика интерфейс явно предлагает `/approve` либо
   продолжение диалога с выбором между вопросом и предложением изменения.
10. После предложения изменения Codex повторно обрабатывает спецификацию, а файл
   обновляется.
11. `/approve` явно завершает flow как успешный и возвращает пользователя в
    основной интерактивный режим; отсутствие этой команды не считается
    утверждением.
12. `Ctrl+C` из любого состояния завершает интерактивный режим Stepan без
    запроса подтверждения.
13. Stepan не создаёт Git commit и не запускает реализацию задачи.
14. После прерывания незавершённую сессию нельзя продолжить; новый запуск
   начинает новый диалог.
15. Оставшийся после прерывания черновик не удаляется автоматически.

Содержимое спецификации принимается как результат диалога с Codex; Stepan в
этой итерации не валидирует набор или порядок её разделов.

Если пользователь вручную изменил файлы после получения ссылки, `/approve`
утверждает их текущее состояние на диске. Перед ответом на вопрос или
подготовкой следующей правки Codex заново читает текущие файлы спецификации.

## 5. Техническая реализация

### 5.1. Владение файлом спецификации

В сценариях создания и изменения черновика Codex разрешено самостоятельно
записывать один или несколько файлов в `docs/specs/<spec-id>/`. Stepan не
получает полный Markdown в structured output и не дублирует запись файлов
средствами контроллера.

`specification.md` обязателен и служит точкой входа. Остальные файлы внутри
каталога необязательны.

После первоначального уточнения Codex сначала возвращает предлагаемый
`spec-id`, но ещё не пишет файлы. Stepan принимает только непустой ID из
ASCII-символов `a-z`, `0-9` и `-`, проверяет, что целевой каталог отсутствует,
и запускает отдельный turn с точным путём и правом записи. Невалидный ID или
существующий каталог завершают flow понятной ошибкой без записи.

`spec-id` ограничен 64 символами и не может совпадать с зарезервированным
Windows device name. Stepan канонизирует Git root и ближайшего существующего
родителя целевого каталога, запрещает выход через symlink, junction или другой
reparse point и повторяет проверку после write-turn.

Codex может читать всё рабочее дерево, но не может записывать вне каталога этой
спецификации. Существование целевого каталога проверяется до turn, которому
разрешена запись.

После turn Stepan обязан проверять фактическое состояние ожидаемого каталога и
отсутствие изменений вне него, а не считать сообщение Codex доказательством
успешной записи.

Stepan должен быть запущен внутри Git working tree, но исходное дерево может
быть грязным: спецификации намеренно остаются без commit. Непосредственно перед
каждым write-turn Stepan фиксирует состояние дерева, после turn сравнивает его с
новым состоянием и принимает результат только тогда, когда все новые изменения
находятся внутри текущего `docs/specs/<spec-id>/`. Изменения, существовавшие до
turn, не считаются нарушением границы.

Workspace всегда равен каноническому корню, полученному через
`git rev-parse --show-toplevel`, даже если Stepan запущен из подкаталога.
Каталог спецификации и отображаемая пользователю ссылка вычисляются
относительно этого корня.

Если после turn обнаружено новое изменение вне разрешённого каталога, Stepan не
утверждает результат и завершает текущий flow ошибкой. Он не откатывает и не
удаляет файлы автоматически; пользователь получает сообщение для ручного
разбора и возвращается в основной интерактивный режим.

Выбор пользователем создания или изменения спецификации является одноразовым
разрешением на запись в каталог текущей спецификации для соответствующего turn.
Stepan автоматически подтверждает file-change approval только для путей внутри
этого каталога. Любая запись вне него, расширение grant или session-wide
разрешение отклоняются без дополнительного вопроса пользователю.

### 5.2. App Server, thread и turn

При запуске интерактивного режима Stepan не запускает Codex. Первый
`codex app-server --stdio` стартует лениво при первой команде `/idea` и затем
переиспользуется до завершения Stepan. Команда `/idea` создаёт новый Codex
thread. Каждое следующее сообщение пользователя внутри flow выполняется
отдельным turn того же thread.

`/approve` завершает текущий flow и освобождает связанный thread на стороне
Stepan, но не останавливает App Server. Следующий `/idea` создаёт новый thread в
том же процессе. `Ctrl+C` завершает App Server и Stepan.

Утверждение является только переходом текущего in-memory flow: Stepan не меняет
файлы, не добавляет status marker и не сохраняет факт approval после завершения
процесса. Перед `/approve` проверяется только наличие обязательного
`specification.md`.

Если App Server аварийно завершился, текущий flow заканчивается понятной
ошибкой без resume, а Stepan возвращается в основной интерактивный режим.
Следующий `/idea` лениво запускает новый App Server и новый thread.

### 5.3. Интерактивный интерфейс

Для интерактивных меню и ввода используется
[`charm.land/huh/v2`](https://github.com/charmbracelet/huh). Дополнительный TUI
framework не вводится.

Новый executable размещается в `cmd/stepan`. Он работает только когда stdin и
stdout подключены к интерактивному терминалу; перенаправленный ввод или вывод
завершает запуск понятной ошибкой. Script, pipe и JSON mode в итерацию не входят.
При установленной переменной `ACCESSIBLE` формы `huh` запускаются во встроенном
accessible mode.

Основной prompt принимает `/idea` как отдельную команду и весь остаток строки
как literal brief без shell quoting. Пустой остаток открывает отдельный
многострочный ввод. Неизвестная команда показывает короткую ошибку и возвращает
основной prompt.

После создания или обновления черновика Stepan показывает ссылку на
`specification.md` и меню:

1. `/approve` — утвердить спецификацию;
2. задать вопрос;
3. предложить изменение.

Второй и третий варианты открывают отдельный текстовый ввод. `Ctrl+C` завершает
Stepan с любого экрана.

Если предложение изменения неоднозначно, Codex возвращает один уточняющий
вопрос без изменения файлов. Stepan получает ответ пользователя отдельным
вводом и запускает следующий turn того же thread; запись разрешается только
когда информации достаточно для изменения.

### 5.4. Process lifecycle

- Поддерживаются Windows native/amd64, macOS native/arm64 и
  `codex-cli 0.147.0`.
- `codex` разрешается через `PATH` без участия shell; несовпадающая версия
  завершает `/idea` ошибкой до создания thread.
- App Server помещается в платформенный supervisor до первого turn: Windows Job
  Object или отдельную Darwin process group. Если containment установить
  нельзя, flow не начинается.
- При `Ctrl+C` во время turn Stepan best-effort отправляет `turn/interrupt`,
  ждёт до трёх секунд и затем закрывает supervisor со всем контролируемым
  деревом процессов.
- При `Ctrl+C` вне turn supervisor закрывается сразу.
- После завершения Stepan App Server и контролируемые supervisor потомки не
  должны оставаться живыми.
- Автоматического timeout turn в этой итерации нет.

### 5.5. Prompt contract

Стартовый prompt и structured output являются частью внутреннего контракта
итерации.

До первого уточняющего вопроса Codex обязан изучить релевантные файлы рабочего
дерева. Он не должен спрашивать пользователя о фактах, которые можно надёжно
получить из кода или документации. Во время первоначального уточнения Codex
задаёт не более одного материального вопроса за turn.

Материальным считается решение, меняющее наблюдаемое поведение, границы или
критерии приёмки. Остальные детали Codex выбирает по существующим соглашениям
репозитория и отражает в первом черновике; пользователь может скорректировать их
через предложение изменения.

Codex ведёт диалог и пишет файлы на языке первоначального idea brief, если
пользователь явно не попросил использовать другой язык.

Каждый turn использует обязательный JSON Schema structured output. Stepan
переходит между состояниями только по валидному enum-результату и не извлекает
команды или статусы из свободного текста. Невалидный structured output завершает
текущий flow понятной ошибкой без автоматического retry; никакая запись не
считается успешной на основании такого ответа.

Стартовый turn получает следующий prompt, где `<idea brief>` подставляется как
пользовательский ввод, а не как инструкция Stepan:

```text
Ты — автор спецификации в интерактивном flow Stepan.

Изучи релевантные файлы текущего Git working tree до первого вопроса.
Не спрашивай о фактах, которые можно надёжно установить из кода и документации.
Не создавай и не изменяй файлы на этапе уточнения.

Уточняй только материальные решения, влияющие на поведение, границы или критерии
приёмки. Задавай не более одного вопроса за turn. Обратимые детали выбирай по
соглашениям репозитория — пользователь сможет изменить их после первого черновика.

Когда информации достаточно, верни READY_TO_WRITE и предложи краткий spec_id
в формате [a-z0-9-]+. До отдельного разрешения Stepan ничего не записывай.

Веди диалог и будущую спецификацию на языке idea brief, если пользователь явно
не попросил иначе.

IDEA BRIEF:
<idea brief>
```

После `READY_TO_WRITE`, валидации `spec-id` и проверки отсутствия каталога
Stepan запускает write-turn с prompt:

```text
Создай цельную спецификацию по результатам текущего диалога.

Разрешённый каталог:
<absolute spec directory>

Обязательно создай specification.md как точку входа. При необходимости можешь
создать дополнительные файлы в этом же каталоге; specification.md должен
ссылаться на них. Не изменяй никакие файлы вне разрешённого каталога и сохрани
все уже существовавшие изменения рабочего дерева.

Фиксированного шаблона нет. Отрази согласованные решения и необходимые детали,
чтобы результат можно было использовать для дальнейшего планирования.

После записи верни WRITTEN.
```

После выбора «предложить изменение» Stepan сначала запускает read-only turn:

```text
Проанализируй предложение пользователя относительно текущей спецификации и
репозитория. Сначала заново прочитай текущие файлы спецификации с диска. Пока не
изменяй файлы.

Если отсутствует материальное решение, верни NEEDS_INPUT и задай ровно один
уточняющий вопрос. Если информации достаточно для согласованной правки, верни
READY_TO_UPDATE.

CHANGE REQUEST:
<request>
```

Ответ на `NEEDS_INPUT` передаётся в следующий read-only turn того же thread с
теми же правилами. Write boundary открывается только после
`READY_TO_UPDATE`.

После `READY_TO_UPDATE` Stepan запускает write-turn:

```text
Внеси согласованное изменение в текущую спецификацию.

Разрешённый каталог:
<absolute spec directory>

Сохрани specification.md точкой входа, согласуй связанные файлы между собой и
не изменяй ничего вне разрешённого каталога. Не перезаписывай несвязанные
изменения пользователя.

После записи верни UPDATED.
```

После выбора «задать вопрос» Stepan запускает read-only turn:

```text
Ответь на вопрос пользователя по текущей спецификации с учётом релевантного
контекста репозитория. Сначала заново прочитай текущие файлы спецификации с
диска. Не изменяй файлы. Если ответ требует предположения, явно обозначь его.

После ответа верни ANSWERED и помести ответ в поле message.

QUESTION:
<question>
```

Structured output использует единый envelope с запретом неизвестных полей:

| `status` | Обязательные дополнительные поля |
|---|---|
| `NEEDS_INPUT` | `message` — ровно один вопрос |
| `READY_TO_WRITE` | `spec_id` |
| `WRITTEN` | нет |
| `ANSWERED` | `message` — ответ пользователю |
| `READY_TO_UPDATE` | нет |
| `UPDATED` | нет |

Для каждого типа turn Stepan передаёт схему только с допустимыми для него
вариантами. Например, question-turn допускает только `ANSWERED`, initial
clarification — `NEEDS_INPUT` или `READY_TO_WRITE`, а write-turn создания —
только `WRITTEN`. `message` и `spec_id` запрещены в состояниях, где они не
указаны таблицей.

### 5.6. Временное использование текущего профиля Codex

По явному решению для этой итерации Stepan использует текущий профиль Codex и
не требует `STEPAN_CODEX_HOME`, отдельного trusted profile или allowlist
effective config, hooks, plugins и MCP. Это локальное dogfood-исключение не
отменяет ADR 0001 и должно быть закрыто до расширения границ MVP.

Принятые риски:

- пользовательские hooks, plugins, MCP и instruction sources могут менять
  поведение turn;
- результат зависит от локального профиля и не полностью воспроизводим на
  другой машине;
- стороннее расширение может получить данные читаемого рабочего дерева или
  добавить вывод в artifacts;
- успешный сценарий не доказывает config isolation;
- режим нельзя использовать с недоверенным репозиторием, production
  credentials или необратимыми внешними эффектами.

Остаются обязательными pinned `codex-cli 0.147.0`, stable App Server contract,
отключённая в turn сеть, write boundary каталога спецификации и платформенный
process containment.

### 5.7. Состояние и artifacts

Stepan не создаёт `.stepan/`, постоянный журнал событий, approvals или raw
App Server artifacts. Активные thread/turn IDs, решения approvals и состояние
интерфейса существуют только в памяти процесса и теряются при завершении.

Сам Codex может сохранить историю созданного thread в текущем профиле. Stepan
не хранит ссылку на неё, не показывает её как возобновляемую сессию и никогда не
использует для resume. Это принято как свойство временного dogfood-режима с
текущим профилем, а не как durable-состояние Stepan.

Это ещё одно принятое ограничение dogfood-среза: после сбоя нельзя восстановить
диалог, доказать durable-порядок approval/operation или получить полный
protocol trace для диагностики. Требование durable approval state из ADR 0001
остаётся незакрытым и должно быть возвращено до расширения границ MVP.

### 5.8. Per-turn permissions

Все turns используют `approvalPolicy="on-request"`, сеть выключена. Read-only
turns уточнения, вопросов и подготовки изменения имеют пустой write allowlist;
любой запрос записи отклоняется.

Write-turn создания или обновления получает ровно один writable root — текущий
`docs/specs/<spec-id>/`. File-change approval внутри него принимается один раз,
в памяти и только для текущего turn. Command, permission amendment, network,
broad и session-wide grants не разрешаются автоматически.

После каждого write-turn Stepan проверяет обязательный `specification.md`,
write boundary и допустимый structured status. Только одновременное выполнение
всех трёх условий переводит flow к пользовательскому меню.

### 5.9. Размещение кода

- `cmd/stepan` — тонкая сборка интерактивного приложения;
- `internal/specflow` — конкретная state machine flow идеи и prompt contracts;
- `internal/agentruntime/codexapp` — существующие transport, correlation и approval policy,
  расширенные long-lived App Server client с несколькими thread/turn;
- `internal/gitsnapshot` и Git CLI — проверка состояния до и после write-turn;
- `charm.land/huh/v2` — единственная новая UI-зависимость.

Существующий `cmd/codex-appserver-probe` и его fixtures остаются рабочими.
Provider interface, общий workflow engine, DSL, prompt registry и persistence
слой не создаются.

Для write-boundary проверки Stepan использует существующий Git-native snapshot
через временный index и сравнивает synthetic tree до и после turn. Настоящий
index, HEAD и существовавшие изменения не модифицируются.

## 6. Проверка реализации

### Автоматические проверки

`go test ./...` не запускает настоящий Codex и проверяет через fake App Server:

- lazy startup, один процесс и несколько последовательных thread/turn;
- переходы всех допустимых structured statuses и отказ на невалидном envelope;
- `/idea` с brief и без него;
- отсутствие файла до `READY_TO_WRITE`;
- валидацию `spec-id` и отказ при существующем каталоге;
- read-only и write-turn approval policy;
- принятие изменений только внутри каталога спецификации при исходно грязном
  working tree;
- обязательный `specification.md` и сохранение partial files при ошибке;
- завершение flow после approval и новый thread для следующего `/idea`;
- возврат в основной режим после падения App Server;
- Windows Job Object cleanup после `Ctrl+C`. macOS process-group cleanup
  проверяется отдельным ручным планом на Apple Silicon.

Интерактивная state machine тестируется отдельно от terminal rendering; тесты
не воспроизводят внутреннее поведение `huh`.

### Live dogfood

Готовый Stepan используется для создания и утверждения спецификации одной
реальной следующей доработки самого Stepan. Конкретная доработка выбирается
перед live-проверкой и не фиксируется этой спецификацией заранее.

Live-проверка подтверждает, что разработчик не открывает интерактивный Codex CLI,
получает вопросы по одному, создаёт первый черновик, задаёт хотя бы один вопрос,
вносит хотя бы одно изменение и завершает flow через approval. Файлы остаются в
рабочем дереве без commit.

## 7. Definition of Done

Итерация завершена, когда одновременно выполнены условия:

- `go test ./...` проходит без сети и без запуска настоящего Codex;
- новый `cmd/stepan` реализует пользовательские истории и критерии приёмки этой
  спецификации;
- pinned version, structured output, write boundary и platform containment gates
  работают fail-closed;
- после `Ctrl+C` не остаётся App Server или его потомков;
- live dogfood создаёт и утверждает спецификацию реальной следующей доработки
  Stepan без открытия интерактивного Codex CLI;
- Stepan не создаёт commit, `.stepan/` или возобновляемое состояние;
- временные отклонения по current Codex profile и durable approval state явно
  остаются известными рисками, а не неявными гарантиями.
