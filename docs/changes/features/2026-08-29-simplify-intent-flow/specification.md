# Stepan: упрощённый flow уточнения intent

Статус: черновик

Идентификатор: `2026-08-29-simplify-intent-flow`

## 1. Цель

Заменить текущий многостадийный `/feature` flow одним продолжительным диалогом,
в котором агент помогает пользователю устранить неоднозначности исходной идеи и
зафиксировать намерение в `intent.md`.

Stepan остаётся оркестратором: создаёт имена и каталоги, ведёт append-only
`mem-log.md`, публикует подготовленный агентом draft, показывает изменения и
применяет их только после решения пользователя. Агент читает Git workspace, но
может записывать только один временный `intent.md` в отдельном каталоге за
пределами проекта.

Результат должен уменьшить число стадий, prompt-шаблонов, output schemas и
переключений permissions без потери контроля над файлами проекта и историей
работы над feature.

## 2. Проблема текущего flow

Текущая реализация разделяет создание, вопрос, анализ изменения и запись
изменения на разные состояния и turns. Для них используются отдельные prompts,
structured statuses и per-turn write policies. Агент при этом продолжает один
и тот же thread, поэтому значительная часть протокола повторно объясняет ему
контекст, который уже присутствует в диалоге.

Кроме того, текущий flow сразу создаёт `specification.md`, хотя на этой стадии
пользователь и агент ещё только уточняют намерение. Это преждевременно смешивает
описание желаемого результата с техническим дизайном, критериями приёмки и
последующим планированием.

Целевой flow должен отделить следующие ответственности:

- агент ведёт содержательный диалог и готовит draft намерения;
- Stepan управляет durable-файлами, review и lifecycle;
- adapter обеспечивает одинаковую изоляцию файлов для любого provider;
- `intent.md` хранит актуальное намерение, а `mem-log.md` — историю его
  формирования.

## 3. Термины

- **Feature** — отдельная пользовательская инициатива, начатая командой
  `/feature` и размещённая в собственном каталоге
  `docs/changes/features/<dated-feature-id>/`.
- **Brief** — исходный свободный текст пользователя при запуске `/feature`.
- **Intent** — уточнённое описание проблемы, желаемого наблюдаемого результата,
  scope и существенных ограничений. Intent не является спецификацией,
  техническим дизайном или планом реализации.
- **`intent.md`** — опубликованное текущее состояние intent.
- **Draft** — полная предлагаемая версия `intent.md`, которую агент записал во
  временный каталог. `draft` также является значением `kind` в structured
  output основной сессии.
- **`mem-log.md`** — человекочитаемый append-only журнал всей видимой переписки,
  решений и событий review для одной feature. Журналом владеет и пишет только
  Stepan.
- **Решение пользователя** — существенный выбор, явно выраженный пользователем
  в brief, ответе, комментарии к доработке или другом сообщении.
- **Решение агента** — существенный выбор или предположение, которое агент
  сделал без отдельного подтверждения пользователя. Такие решения допустимы
  только для нематериальных неоднозначностей и обязаны попасть в `mem-log.md`.
- **Материальная неоднозначность** — неизвестность, способная изменить желаемый
  результат, границы scope или существенные ограничения. До её устранения draft
  создавать нельзя.
- **Artifact root** — созданный Stepan уникальный временный каталог за пределами
  Git workspace, доступный основной agent session для чтения и записи.
- **Публикация** — выполняемое Stepan копирование проверенного draft из artifact
  root в проектный `intent.md`.

## 4. Пользовательские истории

### US-1. Уточнить намерение в одном диалоге

Как разработчик, я хочу обсуждать brief обычными сообщениями без выбора между
режимами «вопрос» и «изменение», чтобы агент сам понимал смысл каждого ввода и
сохранял контекст на протяжении всего flow.

### US-2. Получить intent только после устранения неоднозначностей

Как разработчик, я хочу, чтобы агент сначала изучил репозиторий и задал все
необходимые вопросы, а затем создал `intent.md`, чтобы черновик не содержал
скрытых материальных предположений.

### US-3. Контролировать изменения intent

Как разработчик, я хочу видеть diff каждой последующей версии и явно выбирать
применение, отклонение или доработку, чтобы опубликованный `intent.md` не
менялся без моего согласия.

### US-4. Сохранить историю работы

Как разработчик, я хочу видеть исходный brief, переписку, решения и события
review в append-only `mem-log.md`, чтобы понимать, как сформировалось текущее
намерение и какие альтернативы рассматривались.

### US-5. Получить одинаковое поведение разных adapters

Как пользователь Codex или Claude Code-совместимого CLI, я хочу одинаковый
intent flow и одинаковые файловые ограничения независимо от выбранного
provider.

## 5. Границы

### Входит

- сохранение интерактивной команды `/feature` и literal brief;
- отдельный agent request для короткого осмысленного `feature_id`;
- имя каталога с датой и автоматическим числовым суффиксом при коллизии;
- один основной agent thread на весь intent flow;
- единый bootstrap prompt в начале основной сессии;
- обычный свободный пользовательский ввод во всех состояниях диалога;
- возможность агента задавать один вопрос или небольшой связанный пакет;
- обязательное устранение всех материальных неоднозначностей до первого draft;
- фиксированный `intent.md` в artifact root и отсутствие пути в output;
- немедленная публикация первого валидного draft;
- diff и явное решение пользователя для каждой последующей версии;
- варианты review «применить», «отклонить» и «доработать»;
- append-only `mem-log.md`, которым владеет Stepan;
- структурированные метаданные явных и неявных решений;
- thread-scoped файловая политика: workspace read-only, artifact root
  read-write;
- одинаковая семантика Codex и Claude adapters;
- явное `/approve` для завершения intent flow;
- обновление документации фактического `/feature` flow.

### Не входит

- создание полноценной спецификации, технического дизайна или плана реализации
  внутри intent flow;
- архитектурные решения, декомпозиция задач и детальные критерии приёмки в
  `intent.md`;
- восстановление незавершённого flow после перезапуска;
- восстановление agent thread из `mem-log.md`;
- commit, push или автоматическое начало следующего этапа разработки;
- запись агентом непосредственно в Git workspace;
- полная запись tool calls, system/developer prompts или внутренних рассуждений
  модели;
- несколько draft-файлов или дополнительные файлы intent;
- изменение модели выбора provider и agent executable;
- расширение сетевых, shell- или session-wide полномочий агента.

## 6. Артефакты feature

После получения `feature_id` Stepan создаёт каталог:

```text
docs/changes/features/YYYY-MM-DD-<feature-id>/
```

Например:

```text
docs/changes/features/2026-08-29-simplify-intent-flow/
```

Если имя занято, Stepan последовательно выбирает первый свободный числовой
суффикс:

```text
2026-08-29-simplify-intent-flow-2
2026-08-29-simplify-intent-flow-3
```

Дата является локальной календарной датой процесса Stepan в формате ISO
`YYYY-MM-DD`. Агент возвращает только смысловую часть `feature_id`; дату и
суффикс добавляет Stepan.

Каталог содержит:

```text
docs/changes/features/<dated-feature-id>/
  mem-log.md
  intent.md       # появляется после первого draft
```

`intent.md` всегда один. Дополнительные intent-файлы на этом этапе запрещены.

## 7. Генерация feature ID

До основной сессии Stepan выполняет отдельный read-only agent request. Он
получает исходный brief и возвращает короткий осмысленный идентификатор:

```json
{
  "feature_id": "simplify-intent-flow"
}
```

`feature_id` обязан:

- содержать только `[a-z0-9-]`;
- начинаться и заканчиваться буквой или цифрой;
- быть коротким и отражать смысл brief;
- проходить ограничения длины и Windows reserved names, проверяемые Stepan.

Осознанно принимается риск, что после уточняющего диалога intent может немного
измениться и ранний `feature_id` станет менее точным. Переименование каталога в
рамках этого flow не выполняется.

После валидации Stepan вычисляет dated ID, создаёт каталог feature, создаёт
`mem-log.md` и записывает исходный brief до запуска основной сессии.

## 8. Основная agent session

### 8.1. Lifecycle

Для intent flow создаётся новый thread, отличный от одноразового запроса
feature ID. Этот thread используется для всех уточнений, вопросов, drafts и
доработок до `/approve`, ошибки runtime или отмены.

Первый запрос основной сессии содержит полный bootstrap contract и brief.
Последующие turns получают только новый пользовательский ввод или комментарий
к доработке. Stepan не повторяет отдельные stage prompts для вопросов,
изменений и записи.

Bootstrap contract сообщает агенту:

- назначение intent flow и содержательную границу `intent.md`;
- требование сначала изучить релевантные файлы Git workspace;
- запрет спрашивать о фактах, надёжно устанавливаемых из репозитория;
- требование устранить все материальные неоднозначности до draft;
- возможность задавать вопросы по одному или небольшими связанными пакетами;
- абсолютный artifact root и обязательный путь `<artifact-root>/intent.md`;
- требование перед каждым новым draft заново читать опубликованный `intent.md`
  как авторитетную текущую версию;
- два варианта structured output `message | draft`;
- обязанность перечислять все существенные решения в `decisions`;
- язык brief как язык диалога и `intent.md`, если пользователь явно не указал
  другой.

### 8.2. Содержимое intent

`intent.md` фиксирует:

- проблему или потребность;
- желаемый наблюдаемый результат;
- что входит в scope;
- что явно не входит в scope;
- существенные ограничения.

В `intent.md` не создаётся отдельный журнал принятых решений. Решения влияют на
итоговые формулировки, а их история хранится только в `mem-log.md`.

`intent.md` не должен содержать техническую архитектуру, план реализации,
декомпозицию задач или детальные критерии приёмки. Если без такого решения
невозможно однозначно сформулировать намерение или scope, агент обязан сначала
задать вопрос пользователю.

### 8.3. Вопросы

Stepan не различает специальные режимы вопроса, ответа и запроса изменения.
Любой пользовательский текст передаётся в тот же thread как очередное
сообщение.

Агент самостоятельно выбирает форму уточнения:

- один вопрос, когда ответ влияет на следующий вопрос;
- небольшой пакет, когда вопросы тесно связаны или независимы и пакет не
  ухудшает качество ответов;
- отсутствие вопроса, когда неопределённость нематериальна и агент может
  принять решение, явно вернув его в `decisions`.

## 9. Session-scoped доступ к файлам

До создания основного thread Stepan создаёт уникальный artifact root через
механизм временных каталогов операционной системы. Он находится за пределами
Git workspace.

На весь thread устанавливается неизменная политика:

```text
Git workspace:  read-only
artifact root:  read-write
остальные пути: запрещены
network:         запрещена
shell/commands:  запрещены
```

Политика является частью конфигурации thread, а не параметром отдельного turn.
`specflow` не переключает read-only и write режимы по ходу диалога. Если
конкретный provider требует повторить sandbox-настройки при каждом внутреннем
protocol request, это скрывается внутри adapter и не меняет provider-neutral
интерфейс или семантику flow.

Codex и Claude adapters обязаны поддерживать внешний artifact root одинаково.
Adapter не может молча перенести временный каталог внутрь workspace или
расширить доступ до всего системного temp.

Агент не получает право изменять `intent.md`, `mem-log.md` или другие файлы в
Git workspace. Публикацию всегда выполняет Stepan.

## 10. Structured output

### 10.1. Feature ID request

Одноразовый запрос ID использует отдельный узкий результат из раздела 7.

### 10.2. Основной thread

Все turns основной сессии используют один неизменный envelope с двумя
вариантами.

Обычное сообщение:

```json
{
  "kind": "message",
  "message": "Текст для пользователя",
  "decisions": []
}
```

Подготовленный draft:

```json
{
  "kind": "draft",
  "decisions": []
}
```

Поле `path` отсутствует. При `kind: "draft"` Stepan всегда проверяет
`<artifact-root>/intent.md`.

Каждый элемент `decisions` содержит:

```json
{
  "author": "user",
  "decision": "Краткая однозначная формулировка",
  "rationale": "Почему выбран этот вариант",
  "alternatives": ["Рассмотренная альтернатива"],
  "supersedes": []
}
```

Требования:

- `author` равен `user` или `agent`;
- `decision` и `rationale` непустые;
- `alternatives` обязателен и может быть пустым, если реальных альтернатив не
  было;
- `supersedes` содержит идентификаторы более ранних decision-записей и может
  быть пустым;
- массив `decisions` обязателен в обоих вариантах ответа и может быть пустым;
- неизвестные поля запрещены;
- `message` обязателен только для `kind: "message"` и запрещён для `draft`;
- `kind: "draft"` допустим только после фактического создания или изменения
  временного `intent.md` в текущем turn.

Stepan валидирует JSON Schema и семантические инварианты. Свободный текст вне
structured result не меняет состояние flow. Невалидный envelope или
несоответствие draft-файла контракту завершает текущий flow с понятной ошибкой;
автоматического retry нет.

Provider может технически требовать более широкий runtime-level envelope,
например из-за неизменяемой schema в Claude SDK. Adapter вправе использовать
такой envelope внутри, но `specflow` для одноразового ID request и основного
thread валидирует соответствующие узкие варианты.

## 11. `mem-log.md`

### 11.1. Владение и назначение

`mem-log.md` создаёт и изменяет только Stepan. Агент не получает права записи к
нему и не считается источником истины о факте записи.

Журнал человекочитаем, хранится рядом с `intent.md` и append-only на уровне
логических записей. Уже записанный текст не редактируется и не удаляется.
Отмена или пересмотр оформляются новыми записями со ссылками на прежние.

В этой итерации Stepan не использует журнал для восстановления controller state
или agent context. Потенциальная реконструкция контекста в новой сессии остаётся
совместимым будущим расширением, но не является критерием приёмки.

### 11.2. Содержимое

Stepan немедленно добавляет в журнал после появления:

- исходный brief и каждое последующее видимое сообщение пользователя дословно;
- каждое показанное пользователю сообщение агента дословно;
- каждое решение из structured `decisions`;
- генерацию и выбор dated feature ID;
- создание и публикацию первого draft;
- diff review и выбор «применить», «отклонить» или «доработать»;
- комментарий пользователя к доработке;
- применение или отклонение новой версии;
- финальное `/approve`;
- ошибку или отмену после создания журнала.

System/developer prompts, tool calls, raw protocol events и скрытые рассуждения
модели в `mem-log.md` не записываются.

Каждой decision-записи Stepan присваивает стабильный последовательный
идентификатор. Запись сохраняет автора, формулировку, обоснование, альтернативы
и ссылки `supersedes`. Ссылки на неизвестные или более поздние решения
отклоняются.

Запись пользовательского сообщения выполняется до вызова агента. Сообщение и
решения агента записываются после успешной валидации structured output и до
следующего пользовательского ввода. Ошибка записи журнала блокирует дальнейший
flow: Stepan не продолжает работу с историей, которая перестала быть полной.

## 12. Публикация и review

### 12.1. Первый draft

После первого `kind: "draft"` Stepan:

1. проверяет, что `<artifact-root>/intent.md` существует, является обычным
   файлом и не является ссылкой или escape из artifact root;
2. читает содержимое как draft, не перемещая и не исполняя файл;
3. атомарно создаёт проектный
   `docs/changes/features/<dated-feature-id>/intent.md`;
4. записывает событие публикации в `mem-log.md`;
5. показывает пользователю путь к опубликованному intent и продолжает тот же
   thread.

Отдельное подтверждение первого draft не требуется.

### 12.2. Последующие drafts

Для каждого последующего `kind: "draft"` Stepan сравнивает полный временный
`intent.md` с опубликованным файлом и показывает unified diff. До решения
пользователя project `intent.md` не меняется.

Пользователь выбирает:

- **Применить** — Stepan атомарно заменяет опубликованный `intent.md` draft-ом
  и записывает применение в журнал;
- **Отклонить** — опубликованный файл не меняется, отказ записывается в журнал,
  диалог продолжается;
- **Доработать** — опубликованный файл не меняется, пользователь вводит
  комментарий, Stepan записывает его и передаёт в тот же thread; следующий
  draft снова проходит полный review.

Stepan должен отличать новый draft от оставшегося временного файла предыдущего
turn. `kind: "draft"` без фактически созданной или изменённой в текущем turn
версии не может инициировать повторную публикацию старого содержимого.

### 12.3. Завершение

Команда `/approve` доступна после публикации первого `intent.md`. Она:

1. проверяет наличие обычного проектного `intent.md`;
2. добавляет финальное событие утверждения в `mem-log.md`;
3. завершает основной agent thread;
4. удаляет artifact root;
5. возвращает пользователя в основной prompt Stepan.

`/approve` не создаёт commit и не запускает следующий workflow автоматически.

## 13. Ошибки, отмена и cleanup

- Ошибка генерации или валидации feature ID происходит до создания feature
  directory и не оставляет `mem-log.md`.
- После создания feature directory любая ошибка или отмена добавляется в
  `mem-log.md`, если журнал остаётся доступен для записи.
- Ошибка runtime завершает текущий flow по существующим правилам и закрывает
  нездоровый runtime.
- `Ctrl+C` сохраняет существующее поведение process containment и код выхода
  130.
- Artifact root удаляется после `/approve` и best-effort после штатной ошибки
  или отмены. Остаток системного temp после crash не считается durable state и
  не используется для resume.
- Уже опубликованные `mem-log.md` и `intent.md` не удаляются автоматически при
  ошибке, отмене или завершении процесса.
- Существующие пользовательские изменения Git working tree сохраняются;
  Stepan пишет только в каталог выбранной feature.

## 14. Provider-neutral interface

`internal/agentruntime` предоставляет один seam для Codex и Claude adapters.
Его interface должен позволять создать thread с неизменной конфигурацией:

- bootstrap instructions;
- readable Git workspace;
- единственный writable artifact root либо отсутствие записи;
- output schema логического разговора;
- выключенная сеть и запрещённые внешние команды.

После запуска thread caller передаёт только очередной пользовательский input.
Adapter скрывает provider-specific детали: повторную передачу sandbox policy,
approval callbacks, immutable SDK schema и добавление bootstrap instructions в
первый protocol request.

Ни `specflow`, ни его тесты не должны знать, какой provider фактически выполняет
thread. Оба adapters проходят общий набор conformance-сценариев для внешнего
artifact root, запрета записи в workspace, последовательных turns и
structured output.

## 15. Критерии приёмки

### AC-1. Именование feature

По длинному русскому или английскому brief отдельный agent request возвращает
валидный короткий смысловой `feature_id`. Stepan создаёт каталог с текущей датой
и добавляет минимальный свободный числовой суффикс при коллизии.

### AC-2. Ранний журнал

До запуска основной сессии каталог feature содержит `mem-log.md` с исходным
brief и событием выбора ID, но не содержит `intent.md`.

### AC-3. Один основной thread

Все уточнения, обычные вопросы, изменения и доработки одной feature выполняются
в одном thread. Для них не создаются отдельные question/change/write sessions.

### AC-4. Уточнение до draft

Агент изучает релевантный workspace и не создаёт временный `intent.md`, пока
остаются материальные неоднозначности. Он может задавать вопросы по одному или
небольшими пакетами.

### AC-5. Единый пользовательский ввод

После запуска основной сессии пользователь не выбирает режим вопроса или
изменения. Любой текст передаётся агенту как очередное сообщение того же
диалога.

### AC-6. Session-scoped permissions

На всём протяжении thread агент читает workspace, записывает только внешний
artifact root и не получает per-turn расширений. Попытка записи в workspace,
соседний temp-каталог, через ссылку или за пределы root отклоняется каждым
adapter.

### AC-7. Минимальный envelope

Основная сессия принимает только `kind: "message"` с `message` или
`kind: "draft"` без пути. Оба варианта требуют массив `decisions`; неизвестные
поля и невалидные decision-записи отклоняются.

### AC-8. Первый draft

Валидный первый `<artifact-root>/intent.md` немедленно публикуется как проектный
`intent.md` без отдельного review confirmation и становится доступен
пользователю.

### AC-9. Review изменений

Последующий draft не меняет проект до решения пользователя. Stepan показывает
diff и корректно выполняет все три действия: применить, отклонить и доработать
с комментарием в том же thread.

### AC-10. Полный append-only журнал

`mem-log.md` сохраняет всю видимую переписку, решения с обоснованиями и
альтернативами, а также события review. Пересмотр добавляет новую запись и не
изменяет старую.

### AC-11. Явное завершение

`/approve` записывает утверждение, завершает thread, удаляет artifact root и
возвращает основной prompt без commit или запуска следующего этапа.

### AC-12. Provider parity

Одинаковый автоматический conformance suite проходит для Codex и Claude
adapters. Adapter-specific автотесты подтверждают чтение workspace, запись во
внешний temp и запрет прямой записи project `intent.md`.

### AC-13. Нет resume

После перезапуска Stepan не предлагает автоматически продолжить незавершённый
flow. Существующие `mem-log.md` и `intent.md` остаются обычными project
артефактами.

## 16. Обновляемая документация

Реализация должна согласовать с новым поведением как минимум:

- `docs/feature-flow.md`;
- `docs/changes/features/README.md`;
- актуальные ADR, если фактически меняется принятый runtime interface или
  security model;
- help-тексты и пользовательские названия экранов `/feature`;
- prompt README и встроенные prompt-шаблоны.

Исторические спецификации завершённых изменений не переписываются.
