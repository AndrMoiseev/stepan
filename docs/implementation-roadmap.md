# Stepan: план итераций и роадмап

## Подход к реализации

MVP строится как один жёстко заданный последовательный workflow. На первом этапе не создаются DSL, пользовательская настройка стадий, параллельный scheduler или универсальный adapter API.

Этот роадмап задаёт примерное направление развития, а не строгий план или
обязательство сохранить нумерацию и объём этапов. Авторитетные границы конкретной
итерации определяет её утверждённая спецификация; они могут меняться по
результатам предыдущих итераций и dogfooding.

Работа идёт короткими вертикальными итерациями. Первая пригодная для dogfooding версия должна появиться до завершения полного MVP и использоваться для реализации следующих итераций.

Ориентировочная оценка для одного разработчика:

- первый dogfood-срез: 1–2 недели;
- функционально полный MVP: 3–4 недели;
- подтверждение MVP реальными задачами: 4–6 недель от начала работы.

Оценки являются timebox, а не обязательством. Приоритет — быстро получить наблюдения о реальных отказах и менять control plane на основании этих наблюдений.

## Итерация 0. Технический spike

Оценка: 2–3 дня.

Статус: **завершена, spike passed with caveats**. Решение и обязательные
workarounds: [ADR 0001](adr/0001-codex-app-server-containment.md). Фактические
результаты: [отчёт итерации 0](changes/features/iteration-0/report.md).

Детальный объём, сценарии и критерии готовности зафиксированы в [спецификации итерации 0](changes/features/iteration-0/specification.md).

### Цель

Проверить, что Codex CLI можно использовать как управляемый subprocess, не реализуя собственный агентский runtime.

### Проверяемые возможности

- Запуск `codex app-server --stdio` без shell-интерполяции аргументов.
- Двусторонний JSON-RPC/JSONL transport и server approvals.
- Получение, сохранение и resume thread ID.
- Структурированный финальный ответ через JSON Schema.
- Продолжение сессии.
- Раздельная обработка stdout, stderr и exit code.
- Корректная обработка предупреждений в stderr при успешном exit code.
- Ограничения отмены процесса, timeout и process-tree lifecycle.
- Фактическая граница `readOnly` и role workspace isolation.
- Поведение при невалидном ответе, обрыве и превышении времени.
- Влияние пользовательской конфигурации Codex.
- Quoting, пути и сигналы завершения на целевых ОС.

### Технические решения по итогам spike

- Windows-only MVP с pinned `codex-cli 0.147.0`.
- Source-blind роли в отдельном role workspace без production source.
- Доверенный Codex profile и fail-closed config/plugin/MCP inventory.
- `turn/interrupt` с bounded grace и Windows Job Object containment.
- Durable approval state и append-only журнал событий.
- Candidate snapshot как `HEAD OID + tree OID` через независимый temp-index.

### Результат

- Небольшой probe для запуска Codex.
- Набор записанных успешных и ошибочных JSONL fixtures.
- Зафиксированный внутренний контракт интеграции с Codex.
- Решение по поддерживаемым ОС.

App Server `0.147.0` принят как version-specific transport. Матрица spike
содержит `9 PASS / 4 FAIL / 3 BLOCKED`; отрицательные исходы сохранены как
evidence и закрываются compensating controls ADR 0001, а не broad permissions
или experimental API.

## Итерация 1. Первый walking slice

Оценка: 3–5 дней.

### Цель

Получить первый сквозной сценарий, пригодный для раннего dogfooding.

На этой итерации допускается временное упрощение: задача и критерии приёмки подаются готовым файлом.

### Объём

- Проверка, что текущий каталог является Git-репозиторием.
- Отказ от запуска при грязном рабочем дереве.
- Preflight pinned Codex/schema и allowlisted effective config.
- Windows Job Object containment до начала App Server turn.
- Материализация отдельного role workspace для source-blind ролей.
- Создание run ID.
- Минимальный `state.json`.
- Запись событий запуска Codex.
- Запуск implementation-сессии.
- Выполнение одной или нескольких заранее заданных команд проверки.
- Запуск отдельного read-only verifier.
- Проверка неизменности кандидата во время верификации.
- Создание локального commit после `PASS`.
- Команды `status` и `resume` в минимальном виде.

### Критерий готовности

Stepan реализует, проверяет и коммитит одну настоящую небольшую доработку самого Stepan без запуска интерактивного Codex CLI.

Дополнительно проходят containment invariants ADR 0001: source canary не виден
source-blind роли, после cancel/timeout нет App Server/потомков, а effective
config не содержит незаявленных источников.

С этого момента следующие итерации по возможности выполняются через Stepan.

## Итерация 2. Интерактивная спецификация

Оценка: 3–5 дней.

### Цель

Перенести постановку и уточнение задачи внутрь Stepan.

### Объём

- Интерактивная терминальная сессия.
- Ввод задачи свободным текстом.
- Отдельная specification-role.
- Жёсткая схема проекта спецификации.
- Результат `NEEDS_INPUT` с одним вопросом.
- Ответ оператора и продолжение стадии.
- Команды `approve`, `revise`, `status` и `exit`.
- Сохранение утверждённой спецификации в проект.
- Запрет записи неутверждённого проекта спецификации в project-owned файлы.
- Восстановление диалога после перезапуска Stepan.

### Проверки

- Нельзя перейти к планированию без `approve spec`.
- После изменения проекта спецификации предыдущее одобрение недействительно.
- Материальный открытый вопрос блокирует переход.
- Перезапуск процесса не теряет утверждённый текст и текущий вопрос.

### Dogfooding

Через новый интерактивный flow подготовить спецификацию итерации 3.

## Итерация 3. План и последовательные задачи

Оценка: 4–6 дней.

### Цель

Получить подтверждаемый план и детерминированный последовательный scheduler.

### Объём

- Отдельная planning-сессия Codex.
- Фиксированная схема плана.
- Явное подтверждение плана.
- Сохранение утверждённого плана в проект.
- Planning commit со спецификацией и планом.
- Lifecycle задач плана.
- Последовательный scheduler.
- Связь task ID с acceptance criteria.
- Разрешённые и запрещённые области изменений.
- Проверочные команды на задачу.
- Инвалидация плана при изменении утверждённой спецификации.

### Минимальная схема задачи

- `id`;
- `outcome`;
- `acceptance`;
- `allowed_paths`;
- `forbidden_paths`;
- `verification_commands`;
- `done_when`.

### Критерий готовности

Одна фича Stepan разбивается минимум на три задачи и проходит их последовательно.

## Итерация 4. Верификация, rework и commits

Оценка: 5–7 дней.

### Цель

Довести основной цикл реализации до состояния, в котором агент не может самостоятельно объявить результат готовым.

### Объём

- Свежая implementation-сессия на задачу.
- Передача только утверждённых артефактов и текущего task contract.
- Streaming прогресса в интерфейс Stepan.
- Отмена оператором.
- Проверка неизменности HEAD после работы агента.
- Post-check write boundary.
- Точный candidate snapshot.
- Детерминированные gates.
- Свежая read-only verification-сессия.
- Структурированные blocking findings.
- Результаты `PASS`, `REWORK`, `BLOCKED`, `NEEDS_INPUT`.
- Максимум три полных rework-цикла.
- Локальный commit только после принятия.
- Итоговая верификация всего плана.

### Минимальные классы остановки

- `NEEDS_INPUT`;
- `CODEX_FAILED`;
- `OUTPUT_INVALID`;
- `CHECK_FAILED`;
- `BOUNDARY_VIOLATION`;
- `VERIFICATION_FAILED`;
- `REPOSITORY_DIVERGED`;
- `BUDGET_EXCEEDED`.

Новый код добавляется только тогда, когда для него существует отдельный маршрут реакции.

### Инварианты

- Codex не создаёт commit.
- Verifier не изменяет файлы.
- Проверочные команды берутся из утверждённого плана.
- Повтор получает новую информацию: исправленную спецификацию, новый ответ оператора или конкретные findings.
- Неуспешный gate не может привести к commit.
- Evidence относится к тому же candidate snapshot, который был закоммичен.

## Итерация 5. Recovery и эксплуатационная надёжность

Оценка: 4–6 дней.

### Цель

Сделать состояние workflow авторитетнее агентской сессии и обеспечить восстановление после обрыва.

### Объём

- Append-only журнал событий.
- Атомарное сохранение состояния.
- Восстановление фактов из Git.
- Продолжение после kill на каждой границе workflow.
- Обнаружение расхождения durable-состояния и репозитория.
- Понятный human-readable status.
- Сохранение неуспешного кандидата для rework.
- Запрет автоматического уничтожения изменений.
- Безопасный halt без нового commit.
- Версионирование схем состояния и промптов.

### Обязательные fault-injection тесты

- Kill во время работы Codex.
- Kill между проверкой и верификацией.
- Kill перед commit.
- Codex вернул невалидный JSON.
- Codex завершился с ненулевым кодом.
- Verifier попытался изменить файл.
- Implementation-role изменил неожиданный путь.
- Пользователь изменил репозиторий во время активного run.
- Сохранённое состояние утверждает `PASS`, но Git-факты ему противоречат.

### Критерий готовности

После каждого fault-injection Stepan либо безопасно продолжает run, либо останавливается с одним понятным маршрутом восстановления. Он не создаёт commit и не уничтожает изменения в неоднозначном состоянии.

## Итерация 6. Подтверждение MVP через dogfooding

Оценка: 1–2 недели эксплуатации и исправлений.

### Набор задач

Через Stepan необходимо выполнить не менее десяти реальных задач по развитию самого Stepan, включая:

- изменение документации;
- исправление дефекта;
- локальный рефакторинг;
- небольшую фичу;
- многошаговую фичу;
- задачу, потребовавшую rework;
- задачу, потребовавшую решения оператора.

### Exit criteria MVP

- Не менее 10 реальных задач выполнено через Stepan.
- Минимум 8 из 10 завершены без перехода в базовый Codex CLI.
- Последние пять подходящих задач полностью пройдены внутри Stepan.
- Восстановление после принудительного прерывания проверено минимум на трёх стадиях.
- Ни один commit не создан после проваленного gate или без `PASS`.
- Все commits трассируются до задачи, спецификации, плана и evidence.
- Практически пройдены состояния `REWORK`, `NEEDS_INPUT` и `BLOCKED`.
- Все случаи ручного обхода инструмента классифицированы и превращены в backlog либо явно исключены из границ продукта.

### Собираемые метрики

На MVP метрики нужны для получения baseline, а не для преждевременной оптимизации:

- доля задач, прошедших с первой попытки;
- число rework-циклов;
- длительность стадий;
- причины остановок;
- число вопросов оператору;
- нарушения write boundary;
- доля задач, потребовавших базовый Codex CLI;
- расхождения между deterministic gates и verifier;
- ошибки восстановления.

## Definition of Done для MVP

MVP готов, когда одновременно выполняются следующие условия:

- полный фиксированный workflow работает от свободной постановки до итоговой верификации;
- спецификация и план требуют явного подтверждения;
- каждая задача исполняется и проверяется отдельными Codex-сессиями;
- workflow можно продолжить после перезапуска Stepan;
- commit создаётся только контроллером и только после доказанного `PASS`;
- неподдерживаемая или неоднозначная ситуация приводит к явному halt;
- Stepan реально используется для собственной разработки;
- собраны наблюдения, достаточные для проектирования второго CLI-runner.

## Роадмап после MVP

Дальнейшие пункты обозначены контурно и требуют отдельного проектирования после получения MVP-метрик.

### 1. Поддержка второго агентского CLI

Первый приоритет сразу после MVP.

- Выделить фактический контракт Codex-интеграции в минимальный runner interface.
- Не переносить Codex-специфичные детали в канонический workflow.
- Добавить второй CLI end-to-end через
  [`claude-agent-sdk-go`](https://github.com/severity1/claude-agent-sdk-go).
- Считать целевой интеграцией Claude Code-совместимый CLI, включая корпоративный
  форк, а не только официальный executable `claude`.
- Разрешить явно задать абсолютный путь к CLI. Переданный путь авторитетен: его
  нельзя заменять поиском `claude` в `PATH`, а имя файла и branding строки
  версии не являются признаком совместимости.
- Ограничить встроенные инструменты Claude операциями чтения и записи файлов
  проекта (`Read`, `Write`, `Edit`, `Glob`, `Grep`). Shell, MCP, hooks,
  background tasks и сетевые инструменты в первой версии не поддерживаются;
  внешние инструменты запускает Stepan между ходами агента.
- В первой версии использовать штатное управление процессом SDK без
  собственного process-tree containment. Перед расширением набора инструментов
  пересмотреть это решение по результатам ручной проверки завершения процесса.
- Проверить, что один task/spec/plan contract исполняется обоими CLI.
- Создать conformance suite для structured output, отмены, таймаута, resume, sandbox и событий.

Авторитетные границы зафиксированы в
[спецификации](changes/features/claude-cli-support/specification.md), порядок работ — в
[детальном плане](changes/features/claude-cli-support/implementation-plan.md), а ручная
приёмка на машине с доступом к совместимому CLI — в
[отдельном плане](changes/features/claude-cli-support/manual-test-plan.md).

Абстракция проектируется по двум реальным реализациям, а не заранее.

### 2. Усиление изоляции

- Замена временного отдельного role workspace на native restricted roots только
  после повторных live-сценариев и пересмотра ADR 0001.
- Превентивные path capabilities вместо одного post-check.
- Network policy.
- Изоляция credentials.
- Secret scanning.
- OS-level sandbox.
- Trusted framework configuration, которую candidate не может изменить.

### 3. Независимый Test Worker и риск-зависимая проверка

- Разделение генерации кода и тестов.
- Отдельный test contract.
- Проверка качества тестов.
- Risk profiles.
- Adversarial verifier для задач с высокой ценой ошибки.

### 4. Настраиваемые workflow

- Несколько встроенных проверенных workflow.
- Project profiles.
- Декларативная настройка ролей, gates и бюджетов.
- Полноценный DSL только после доказанной необходимости.

### 5. Model routing и собственные evals

- Разные модели по функциональным ролям.
- Версионирование профилей моделей и промптов.
- Сравнение first-pass rate, rework, стоимости и defect escape.
- Regression fixtures из реальных инцидентов Stepan.

### 6. Кроссплатформенная полировка и installer

Нативный runtime для macOS/arm64 добавлен отдельным compatibility change после
первого walking slice. Остаются:

- Linux и Intel Mac;
- единое поведение subprocess, сигналов и путей;
- диагностика установки Codex и Git;
- безопасное обновление framework-owned файлов.

### 7. Task graph, worktrees и параллелизм

- Граф зависимостей задач.
- Изолированный worktree на задачу.
- Write-set conflict detection.
- Последовательные conflict zones.
- Ограниченный параллелизм после измерения его реальной пользы.

Worktree здесь является механизмом Git-организации и conflict isolation, а не
границей чтения production source.

### 8. PR, CI и delivery-интеграции

- Создание PR.
- CI evidence, привязанное к candidate SHA.
- Инвалидация approvals после изменения SHA.
- Merge coordination.
- Push и внешние мутации только через отдельную policy и явные полномочия.

### 9. Learning loop и эксплуатационные evals

- Автоматический сбор причин rework и остановок.
- История изменений workflow и промптов.
- Incident fixtures.
- Сравнение релизов Stepan на замороженном наборе задач.
- Изменение framework только при наличии наблюдавшегося отказа или измеримой цели.
