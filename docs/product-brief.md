# Stepan: продуктовый бриф и границы MVP

## Контекст

Stepan — локальный CLI-инструмент для управляемой разработки ПО через существующие агентские CLI.

Агенты рассматриваются как вероятностные и ненадёжные исполнители. Stepan не пытается воспроизводить их внутреннюю логику или сделать генерацию детерминированной. Вместо этого он создаёт детерминированный control plane: явно управляет состояниями, полномочиями, проверками, бюджетами, фиксацией результата и восстановлением после сбоев.

Первая версия работает только с Codex CLI. Интеграция с ним намеренно реализуется напрямую, без преждевременного adapter API. Поддержка других агентских CLI — первый приоритет после MVP.

## Цель продукта

Позволить разработчику пройти значимую часть локального цикла разработки внутри одной интерактивной сессии:

```text
задача → спецификация → план → код → проверки → локальные commits
```

При этом:

- переходы между стадиями определяет код Stepan;
- решения оператора, состояние Git и результаты проверок важнее рассказа агента;
- ошибки приводят к ограниченному rework, остановке или вопросу оператору;
- после сбоя процесс можно продолжить без ручного восстановления агентского контекста;
- успешно проверенный результат фиксируется локальным commit;
- взаимодействовать с базовым Codex CLI для поддерживаемых задач не требуется.

Детерминированной должна быть процедура разработки, а не генерируемый код.

## Целевой пользователь MVP

Разработчик, который:

- работает в локальном Git-репозитории;
- использует Codex CLI;
- готов подтверждать спецификацию, план и материальные решения;
- хочет делегировать реализацию, проверки и rework, не теряя управляемость процесса;
- работает над задачами без необратимых production-эффектов.

## Основные продуктовые принципы

### Stepan управляет workflow

Codex не выбирает следующую стадию, не закрывает задачу и не создаёт commit. Он выполняет ограниченную роль и возвращает структурированный результат. Решение о переходе принимает Stepan по состоянию репозитория, формальным ответам роли и результатам проверок.

### Агентский вывод — недоверенные данные

Текст `«всё готово»` не является доказательством. Stepan отдельно проверяет фактический diff, разрешённую область изменений, команды проверки и результат независимой верификации.

### Спецификация и план подтверждаются человеком

До изменения кода существуют два обязательных gate:

1. `approve spec`;
2. `approve plan`.

Неопределённое материальное решение возвращается оператору одним вопросом за раз. Молчание не считается согласием.

### Состояние переживает агентскую сессию

Спецификация и план являются файлами проекта. Служебное состояние, события, вывод ролей и evidence хранятся отдельно в `.stepan/`. Возобновление строится по durable-состоянию и фактам Git, а не по памяти модели.

### Изменения локальны и обратимы

MVP работает в текущем checkout и использует только последовательное выполнение. Новый run начинается только на чистом рабочем дереве. После каждой успешно проверенной задачи Stepan создаёт локальный commit, но никогда не делает push.

## Что делает MVP

- Работает с Codex CLI, захардкоженным как единственный исполнитель.
- Запускается в локальном Git-репозитории.
- Требует чистое рабочее дерево перед началом нового run.
- Принимает задачу на естественном языке.
- Ведёт интерактивную терминальную сессию.
- Помогает последовательно разработать спецификацию.
- Задаёт оператору вопросы по одному.
- Требует явного подтверждения спецификации.
- Строит последовательный план реализации.
- Требует явного подтверждения плана.
- Сохраняет утверждённые спецификацию и план как файлы проекта.
- Выполняет задачи плана последовательно.
- Использует отдельные сессии Codex для разных ролей.
- Запускает детерминированные проверки.
- Независимо верифицирует результат каждой задачи.
- Ограничивает количество rework-попыток.
- После успешной задачи создаёт локальный commit.
- Не делает push.
- Хранит служебное состояние, события и evidence в `.stepan/`.
- Показывает понятный статус и умеет продолжить прерванный run.
- Завершает весь план итоговой верификацией.

## Что не делает MVP

- Не реализует собственный агентский runtime — ни сейчас, ни в будущем.
- Не вызывает API моделей напрямую.
- Не поддерживает другие агентские CLI.
- Не содержит публичный adapter API или универсальную provider-абстракцию.
- Не поддерживает настраиваемые workflow и DSL.
- Не выполняет задачи параллельно.
- Не использует Git worktree.
- Не управляет PR, push, merge, CI и релизами.
- Не работает с production и необратимыми внешними эффектами.
- Не содержит отдельного Test Worker: в MVP implementation-role может менять код и тесты.
- Не выполняет сложный risk-based routing и adversarial verification.
- Не гарантирует корректность кода.
- Не принимает продуктовые или иные материальные решения за оператора.
- Не обещает физическую изоляцию отдельных каталогов внутри репозитория. В MVP нарушение write boundary обнаруживается до commit и останавливает pipeline.

## Граница применимости MVP

Первоначально поддерживаются задачи, которые:

- выполняются целиком в локальном репозитории;
- не требуют production credentials;
- не имеют необратимых внешних эффектов;
- допускают проверку локальными командами;
- могут быть разбиты на последовательные commit-sized задачи;
- не требуют параллельного изменения независимых ветвей проекта.

Задачи вне этой границы должны завершаться понятным `BLOCKED`, а не исполняться в частично поддерживаемом режиме.

## Фиксированный workflow MVP

```text
new
→ specification
→ awaiting_spec_approval
→ planning
→ awaiting_plan_approval
→ executing_task
    → deterministic_checks
    → independent_verification
    → rework | commit | blocked
→ final_verification
→ completed | blocked | failed
```

### Постановка задачи и спецификация

Оператор описывает задачу свободным текстом. Отдельная сессия Codex формирует проект спецификации:

- ожидаемый результат;
- текущее и новое поведение;
- scope и anti-goals;
- ограничения;
- критерии приёмки;
- неизвестные и требуемые решения;
- предполагаемые способы проверки.

Если информации недостаточно, Stepan показывает оператору один вопрос. После ответа продолжается та же стадия.

Модель не пишет утверждённую спецификацию непосредственно в проект. Она возвращает структурированный проект, а Stepan сохраняет файл только после команды оператора `approve`.

### Планирование

Новая сессия Codex читает утверждённую спецификацию и репозиторий и строит последовательный план. Каждая задача содержит:

- стабильный ID;
- один проверяемый outcome;
- связанные acceptance criteria;
- ожидаемые файлы или области изменений;
- запрещённые области;
- команды проверки;
- условия завершения.

После подтверждения Stepan сохраняет план и создаёт отдельный planning commit со спецификацией и планом. Это возвращает репозиторий в чистое состояние перед реализацией.

### Реализация задачи

Для каждой задачи Stepan запускает свежую сессию Codex в режиме `workspace-write`.

Codex получает:

- утверждённую спецификацию;
- утверждённый план;
- текущую задачу;
- локальные инструкции проекта;
- разрешённую область изменений;
- заранее согласованные проверки.

### Детерминированные gates

После завершения агента Stepan сам проверяет:

- HEAD не был изменён агентом;
- рабочее дерево содержит только ожидаемые изменения;
- нет изменений вне разрешённой области;
- структурные команды завершились успешно;
- утверждённые тестовые команды прошли;
- кандидат не изменился во время проверок.

Команды берутся из подтверждённого плана, а не исполняются из произвольного финального сообщения агента.

### Независимая верификация

Свежая read-only сессия Codex получает:

- спецификацию;
- задачу плана;
- фактический diff;
- результаты проверок;
- точный идентификатор снимка кандидата.

Она возвращает один из структурированных результатов:

- `PASS`;
- `REWORK`;
- `BLOCKED`;
- `NEEDS_INPUT`.

Verifier не может изменять код. При `REWORK` запускается свежая implementation-сессия с конкретными замечаниями. Первоначальный лимит — три полных rework-цикла.

### Commit

Только Stepan создаёт commit, и только если:

- проверки успешны;
- verifier вернул `PASS`;
- кандидат не изменился после проверки;
- diff соответствует задаче;
- рабочее дерево после commit снова чистое.

Evidence связывается с точным снимком кандидата и итоговым commit SHA.

### Итоговая верификация

После всех промежуточных commits отдельная сессия проверяет весь результат против спецификации и плана, включая межзадачные эффекты. Если обнаружен дефект, Stepan создаёт корректирующую задачу либо блокирует run.

## Критерий успеха MVP

Главная продуктовая гипотеза:

> Разработчик может выполнить реальную многошаговую задачу, не выходя из Stepan, а ненадёжность Codex проявляется как наблюдаемый и маршрутизируемый отказ, а не как незаметно принятый плохой результат.

MVP считается подтверждённым только после dogfooding на развитии самого Stepan. Подробные критерии и план проверки описаны в [плане итераций и роадмапе](implementation-roadmap.md).
