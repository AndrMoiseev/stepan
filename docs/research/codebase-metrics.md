# Метрики кодовой базы Stepan: способы сбора

Исследование от 2026-09-20. Фокус — качество и архитектура Go-кода: размер и сложность единиц кода, зависимости пакетов, диагностики анализаторов и покрытие тестами. История Git может помочь найти часто меняющиеся участки. Пороги, дашборд и новые проверки CI здесь не назначаются.

## Контекст измерения

Это Go-модуль с Go 1.26.5; быстрые тесты запускаются как `go test ./...`, а наборы `git_integration` и `process_integration` — отдельно ([инструкции репозитория](../../AGENTS.md), [CI](../../.github/workflows/ci.yml)). CI уже запускается на Windows/amd64 и macOS/arm64. [Правила импортов](../../arch-go.yml) проверяются тестом [internal/architecture](../../internal/architecture/architecture_test.go). Для сопоставимых снимков нужно сохранять commit SHA, Go и версии внешних инструментов, GOOS/GOARCH, build tags, набор файлов и исключения. Это особенно важно для файлов с платформенными суффиксами и тестов с build tags: Go выбирает исходники по параметрам сборки ([документация `go` и флага `-tags`](https://pkg.go.dev/cmd/go)).

| Область | Что измерять и как собрать | Что означает и где граница |
|---|---|---|
| Размер и состав | Количество отслеживаемых файлов: `git ls-files -z`; Go-пакеты и состав компиляции: `go list -json ./...`; строки кода/комментариев/пустые строки по языкам: [scc](https://github.com/boyter/scc) с явно заданными исключениями. | Файлы и физические строки показывают размер и состав дерева, а не сложность или качество. `git ls-files` по умолчанию перечисляет файлы из индекса; `go list` учитывает условия сборки; счётчик строк может захватить тесты, генерируемые файлы, документацию и артефакты, если их не отделить ([Git](https://git-scm.com/docs/git-ls-files), [Go](https://pkg.go.dev/cmd/go), [scc](https://github.com/boyter/scc)). |
| Покрытие тестами | `go test -count=1 -coverprofile=coverage.out ./...`; разбор `go tool cover -func=coverage.out` или `-html=coverage.out`. Для охвата сценариев с реальными процессами — отдельные профили при соответствующих build tags; для запущенного CLI возможны `go build -cover` и `GOCOVERDIR`. | Процент **операторов Go, выполненных конкретным набором тестов**. Он не показывает качество утверждений или покрытие всех сценариев. Без отдельного запуска интеграционные файлы здесь исключены; сравнивать профили следует только при одинаковых tags/пакетах/платформах. Инструментирование влияет на выполнение тестов ([Go coverage](https://go.dev/doc/build-cover), [Go cover](https://go.dev/cmd/cover/)). |
| Статический анализ | `go vet ./...`; при необходимости дополнительный [Staticcheck](https://staticcheck.dev/docs/getting-started/) на тех же пакетах и build tags. Считать диагностики по инструменту и правилу, фиксируя версию. | Это найденные подозрительные конструкции, а не оценка здоровья кода. `go vet` применяет эвристики и не гарантирует отсутствие ошибок; набор проверок Staticcheck меняется, поэтому абсолютное число диагностик между версиями не сопоставимо без оговорки ([Go vet](https://go.dev/cmd/vet/), [Staticcheck CLI](https://staticcheck.dev/docs/running-staticcheck/cli/)). |
| Сложность функций | [gocyclo](https://github.com/fzipp/gocyclo) для списка функций с высокой цикломатической сложностью; для когнитивной сложности есть `gocognit` в [golangci-lint](https://golangci-lint.run/docs/linters/configuration/). | gocyclo считает базовую единицу плюс `if`, `for`, `case`, `&&`, `||`: это приближение числа независимых путей, удобное для поиска функций на ручной разбор. Когнитивная сложность пытается оценить понятность потока управления, но методики разных инструментов смешивать нельзя; ни одна не измеряет сложность домена ([gocyclo](https://github.com/fzipp/gocyclo), [Sonar: complexity](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/metric-definitions)). |
| Архитектура и зависимости | Уже доступен проход/нарушение правил Arch-Go через `go test ./internal/architecture`; [Arch-Go](https://github.com/arch-go/arch-go) также различает compliance правил и coverage **пакетов правилами**. Фактические `Imports` из `go list -json ./...` позволяют отдельно считать внутренние рёбра, входящие/исходящие зависимости и пакеты с высокой связностью. | Архитектурный coverage — доля пакетов, охваченных правилами, **не покрытие тестами**. Существующая [карта контекстов](../architecture/context-map/context-map.md) показывает **разрешённые** импорты, поэтому её нельзя принимать за граф фактических импортов. Число рёбер само по себе не определяет правильность границ ([Arch-Go](https://github.com/arch-go/arch-go), [Go list](https://pkg.go.dev/cmd/go)). |
| Вспомогательный сигнал: изменчивость Git | `git log --since=2026-01-01 --numstat --format= -- cmd internal` даёт добавленные/удалённые строки по commit и пути; `--name-only` даёт частоту изменений файлов. Считать по фиксированному интервалу и пути. | Churn истории помогает расставить приоритеты ручного разбора сложных файлов, но не измеряет качество. Переносы/форматирование завышают оценку; двоичные файлы имеют `-` вместо чисел, а неполная история clone занижает её. Для CI-среза истории нужен полный fetch (в [job `changes`](../../.github/workflows/ci.yml) он уже задан как `fetch-depth: 0`) ([Git log](https://git-scm.com/docs/git-log)). |

## Дополнительные правила сопровождаемости и модульности

Для пакетов Go полезно отдельно считать: число production-файлов и строк на пакет/файл, число внутренних импортов каждого пакета (*исходящая связность*) и число пакетов, импортирующих его (*входящая связность*). Источник фактических импортов — поле `Imports` в `go list -json ./...`; при подсчёте нужно исключить стандартную библиотеку и внешние модули и явно решить, учитывать ли импорты тестов. Это **сигналы для разбора**: большой `impl_loop` либо высокая входящая связность инфраструктурного пакета не доказывают плохую декомпозицию. Конкретное архитектурное правило уже есть: запрещённые направления импортов в [arch-go.yml](../../arch-go.yml), проходящие через [архитектурный тест](../../internal/architecture/architecture_test.go). Для него можно записывать число нарушений и долю пакетов, на которые попало хотя бы одно правило Arch-Go; ноль нарушений при неполном охвате правил не равен полной архитектурной проверке ([Go list](https://pkg.go.dev/cmd/go), [Arch-Go](https://github.com/arch-go/arch-go)).

Историческая *связанность изменений* дополняет граф импортов: если два пакета часто приходится менять в одном commit, их граница может требовать разбора даже без прямого импорта. [CodeScene](https://codescene.io/docs/terminology/codescene-terminology.html) считает change coupling на уровне файлов и архитектурных компонентов. Массовые форматирования и сквозные миграции создают ложный сигнал, поэтому связность изменений следует проверять на конкретных commits, а не считать самостоятельным дефектом.

Повторяющиеся фрагменты можно собирать через Sonar `duplicated_lines_density = duplicated_lines / lines × 100` или через `dupl` в [golangci-lint](https://golangci-lint.run/docs/linters/). Sonar для языков, кроме Java, ищет блоки от 100 повторяющихся токенов на не менее чем 10 строках Go; мелкие повторы под этот порог не попадут. Доля дубликатов особенно зависит от исключений для generated-файлов и тестов. Правило «нет новых дублированных блоков» точнее фиксирует желаемое поведение, чем общий процент без заданной области подсчёта ([Sonar metric definitions](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/metric-definitions)).

## Безопасность Go-кода и зависимостей

| Инструмент | Что даёт и пример запуска | Ограничение и цена применения |
|---|---|---|
| [govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck) | `govulncheck ./...` ищет **известные** уязвимости зависимостей и стандартной библиотеки, сужая результат до вызовов достижимых уязвимых функций; `-tags`/`-test` меняют область, `-mode binary` проверяет собранный артефакт. Возможное правило: число подтверждённых достижимых уязвимостей = 0. | Требует обновляемой [Go vulnerability database](https://go.dev/doc/security/vuln/database) и сетевого доступа либо зафиксированного локального снимка через `-db`. `reflect`, `unsafe` и консервативный анализ интерфейсов ограничивают точность. Вывод `-json`/SARIF **возвращает exit code 0 даже при находках**: для автоматического вердикта надо анализировать результат, а не только код возврата ([документация CLI](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck)). |
| [CodeQL](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning) | Запросы находят потенциальные ошибки и уязвимые потоки данных в Go; результат — alert с правилом и серьёзностью. Возможное правило: нет новых alert высокой серьёзности после ручной оценки. | Для Go база CodeQL обычно создаётся через `autobuild` или явно заданную сборку; охвачены файлы, прошедшие через выбранную сборку. Требуются дополнительный GitHub Actions run/минуты; доступность GitHub code scanning зависит от типа репозитория и лицензии ([сборка Go](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-for-compiled-languages), [доступность](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning)). |
| [gosec](https://github.com/securego/gosec) | Локальный анализ AST/SSA Go с правилами безопасности, в том числе обработка путей, запуск команд, криптография, taint analysis; `gosec ./...`, JSON/SARIF для результатов. Возможное правило: нет новых подтверждённых находок по выбранным G-правилам. | Дополнительный бинарник и время анализа, возможны ложные срабатывания. Для Stepan особенно уместен ручной разбор правил о путях и командах, потому что CLI работает с Git и дочерними процессами. Правила/исключения и версию нужно закреплять; инструмент не заменяет поиск известных CVE в зависимостях ([gosec README](https://github.com/securego/gosec)). |
| [golangci-lint](https://golangci-lint.run/docs/linters/) | Один запуск для выбранных `gocognit`, `cyclop`, `dupl`, `gosec`, `depguard` и других проверок; агрегирует диагностики, но сам по себе не создаёт единого балла качества. | Нужна явная конфигурация и закреплённая версия. Для Go 1.26.5 важно выбрать релиз, собранный с совместимой версией Go; новые Go-релизы не поддерживаются автоматически. Изменения состава линтеров меняют сравнимость серий ([FAQ](https://golangci-lint.run/docs/welcome/faq/), [CI install](https://golangci-lint.run/docs/welcome/install/ci/)). |

`govulncheck` и CodeQL/gosec покрывают разные классы рисков: известные уязвимости используемых Go-пакетов и подозрительные конструкции собственного кода. Нулевое число находок любого одного сканера означает лишь «ничего не найдено его базой и правилами при данной конфигурации» ([Go vulnerability management](https://go.dev/doc/security/vuln/), [CodeQL](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning), [gosec](https://github.com/securego/gosec)).

## Составные оценки и итоговые вердикты

| Подход | Точное значение | Применимость к Stepan |
|---|---|---|
| [SonarQube Cloud](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/metric-definitions) | Рейтинг сопровождаемости A–E выводится из **оценённого времени исправления замечаний / (условная стоимость создания строки × число строк)**. По умолчанию стоимость строки — 30 минут, A соответствует доле долга ≤5%, B — от 5% до <10% и далее по шкале. Рейтинги безопасности и надёжности определяются самой серьёзной найденной проблемой; это другие шкалы, не среднее всех величин. `coverage` Sonar смешивает покрытие строк и условий и не тождественно `go tool cover` (покрытию операторов). | Объединяет размер, сложность, повторы, замечания и загруженное покрытие в нескольких показателях, но **не даёт одного объективного индекса здоровья**. Область «нового кода», quality profile и оценки времени исправления определяют результат. Sonar импортирует Go coverage profile, не запускает Go-тесты сам ([метрики](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/metric-definitions), [импорт покрытия](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/test-coverage/go-test-coverage)). |
| [CodeScene Code Health](https://codescene.io/docs/guides/technical/code-health.html) | Оценка сопровождаемости файла от 1 до 10 объединяет признаки сложности и организации кода; поддержка Go заявлена как полная. Hotspots и change coupling из истории Git показывают, на каких файлах и архитектурных компонентах ухудшение здоровья вероятнее повлияет на работу. | Даёт именно интегральный показатель с разбором причин, но это оценка по модели конкретного продукта, а не независимое измерение модульности или безопасности. Для сравнения во времени нужно сохранять версию анализа, историю и настройки компонентов; изменение границ компонентов меняет итог ([терминология](https://codescene.io/docs/terminology/codescene-terminology.html), [поддержка Go](https://codescene.io/docs/usage/language-support.html)). |
| [Sonar quality gate](https://docs.sonarsource.com/sonarqube-cloud/standards/managing-quality-gates/introduction-to-quality-gates) | Логическое **pass/fail** из конкретных условий, а не калиброванный числовой балл. Встроенный Sonar way для нового кода включает рейтинги безопасности, надёжности, сопровождаемости A; review всех новых security hotspots; покрытие ≥80%; дублирование ≤3%. В pull request применяются только условия на новый код. | Это пример набора правил, **не предложение включить такие пороги сейчас**. По умолчанию условия покрытия и дублирования игнорируются при менее чем 20 новых строках. Вывод gate нужно читать вместе с числами и перечнем замечаний; он не оценивает Go-архитектуру из `arch-go.yml` ([quality gates](https://docs.sonarsource.com/sonarqube-cloud/standards/managing-quality-gates/introduction-to-quality-gates)). |
| [OpenSSF Scorecard](https://github.com/ossf/scorecard) | Несколько эвристик безопасности **репозитория и цепочки поставки** получают 0–10; общий балл — взвешенное по риску среднее. Проверки включают CI, review, права токенов, обновление зависимостей и другие практики. | Полезен как отдельная оценка процессов разработки и публикации, но мало говорит о модульности Go и не заменяет `govulncheck`. Авторы прямо предупреждают, что агрегат скрывает разные комбинации проблем, а эвристики дают ложные срабатывания; запуск по GitHub требует API-доступа и обычно токена из-за лимита запросов ([Scorecard README](https://github.com/ossf/scorecard)). |

SonarQube **Cloud** [указывает поддержку Go 1.0–1.27](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/languages/go) и сканер на Windows x86-64 или macOS; это покрывает Go 1.26.5 Stepan. Страница SonarQube **Server** пока [указывает только Go 1.0–1.25](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/languages/go), так что конкретный серверный релиз надо проверить отдельно. Cloud добавляет сервис, учётную запись, токен и шаг отправки анализа; его возможности/стоимость зависят от плана и объёма приватного кода ([сканеры](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/scanners), [планы](https://docs.sonarsource.com/sonarqube-cloud/administering-sonarcloud/managing-subscription/subscription-plans)). Нативные Go/Arch-Go команды можно запускать в существующих Windows/macOS jobs без внешнего сервиса; сетевые и платформенные условия нужно отдельно сохранить в метаданных снимка.

Для собственных интегральных баллов Stepan пока нет калибровки. Сложение процентов покрытия, количества уязвимостей, сложности и графовых степеней в одно число требует явных весов и доказательства, что этот балл связан с реальными затратами на изменение или дефектами. До такой проверки надёжнее показывать **вектор измерений**: нарушения архитектурных правил, размер/сложность и дублирование по пакетам, coverage по наборам тестов, диагностики анализаторов и проверенные уязвимости. При необходимости поверх него можно задать прозрачный операционный вердикт из конкретных правил; такой вердикт является политикой проекта, а не универсальным измерением качества. Разницу между полезными индивидуальными проверками и малоинформативным агрегатом подчёркивают и [авторы OpenSSF Scorecard](https://github.com/ossf/scorecard).

## Кандидаты для локальной сборки

### Локальный набор для запуска в сборке

Если приоритет — автоматический запуск без внешнего сервиса, ближайший набор: `go test` и профиль покрытия по каждому набору build tags, `go vet`, уже действующий архитектурный тест с `arch-go.yml`, закреплённый выпуск `staticcheck`, затем `govulncheck` и при необходимости `gocognit`/`gocyclo`. `go list -json ./...` даёт исходные данные для собственного отчёта об импортах, но критерии модульности придётся сформулировать отдельно. Staticcheck даёт диагностики по правилам, а не числовую оценку сложности или архитектуры. `govulncheck` запускается локальным бинарником, но для актуальных сведений обращается к базе уязвимостей; полностью автономный и воспроизводимый запуск требует локального снимка базы и фиксации его даты. Это список кандидатов для пилотного замера, без предложенных порогов CI ([Go list](https://pkg.go.dev/cmd/go), [Staticcheck CLI](https://staticcheck.dev/docs/running-staticcheck/cli/), [govulncheck CLI](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck)).

### Go-Architect и Staticcheck для headless CI

Для `govulncheck` в сборке существенен формат результата: в обычном текстовом режиме найденные уязвимости дают ненулевой код завершения, но `-json` и SARIF завершаются кодом 0 даже при находках. Если сохранять машинный отчёт, критерий CI должен читать сами findings. По умолчанию инструмент обращается к `vuln.go.dev`; `-db` допускает `file://` со снимком базы ([CLI](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck), [база уязвимостей](https://go.dev/doc/security/vuln/database)).

Определения архитектурных чисел Go-Architect важны для интерпретации. Для пакета `Ca` — число импортирующих его пакетов, `Ce` — число импортируемых им пакетов внутри системы, `I = Ce/(Ca+Ce)`; при `Ca+Ce = 0` проект назначает `I = 0`. Его эвристика абстрактности считает **и интерфейсы, и структуры** абстракциями: `A = (interfaces + structs)/(interfaces + structs + functions + methods)`, а удаление от «главной последовательности» — `D = |A + I − 1|`. Поэтому высокий/низкий `A`, `I` или `D` сам по себе не является доказательством хорошей декомпозиции Go-кода. Матрица зависимостей предлагает булевы и взвешенные ячейки, но точная формула весов в [документации матрицы](https://go-architect.github.io/docs/analysis-tools/dependency-structure-matrix/) не описана. Показатель dependency coupling считает инструкции, использующие выбранную зависимость, а не количество рёбер импорта ([формулы](https://go-architect.github.io/docs/analysis-tools/instability-and-abstractness/), [coupling](https://go-architect.github.io/docs/analysis-tools/dependency-coupling/)).

Зрелость и переносимость Go-Architect требуют проверки: в [инструкции установки](https://go-architect.github.io/docs/install/) указан Go 1.19, последний [тег приложения](https://github.com/go-architect/go-architect/releases) — `v0.5.4` от декабря 2023 года; просмотренная [история main](https://github.com/go-architect/go-architect/commits/main/) заканчивается коммитом декабря 2024 года. Это не подтверждает работу приложения и библиотеки с Go 1.26.5 или на текущих Windows/amd64 и macOS/arm64. В приложении `gocyclo` и `gocognit` запускаются как внешние процессы; Git-анализ зависит от выбранного периода в месяцах и потому меняется со временем даже без изменения исходного кода ([исходный API](https://github.com/go-architect/go-architect/blob/main/api.go), [VCS Analysis](https://go-architect.github.io/docs/analysis-tools/vcs-analysis/)).

## Возможный первый снимок

Без новых зависимостей можно собрать пакетный состав (`go list -json`), обычный профиль покрытия, `go vet` и результат существующего архитектурного теста. Следующий слой — закреплённые версии измерителя сложности/дублирования и `govulncheck`; Sonar, CodeQL и Scorecard требуют отдельного решения об инфраструктуре и объёме анализа. Git churn оставить вспомогательным сигналом для выбора файлов на разбор. Результаты Windows и macOS следует хранить с указанием платформы и набора tags, а покрытие обычных и интеграционных тестов показывать раздельно, пока не определена корректная процедура объединения профилей.
