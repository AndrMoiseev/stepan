# Ошибки

Применение: создание, передача, проверка и логирование ошибок; panic/recover.

## Правила

1. Обязательно принимайте решение для каждой возвращаемой ошибки: обработать, передать или осознанно проигнорировать. Причина игнорирования должна быть понятна из контракта или короткого комментария.
2. Добавляйте контекст через `fmt.Errorf("operation: %w", err)`, когда он помогает определить операцию или объект сбоя. Прозрачный forwarding допускает `return err`.
3. Обязательно рассматривайте `%w` как раскрытие причины вызывающему коду. На границе модуля сохраняйте либо переводите ошибку согласно его контракту; одного факта пересечения границы недостаточно для потери цепочки.
4. Для распознавания ошибок в цепочке используйте `errors.Is` и `errors.As`. Сравнение текстов допустимо только при проверке самого текстового контракта.
5. Используйте sentinel, когда вызывающему коду нужен устойчивый признак состояния; тип ошибки — когда нужны структурированные данные. Не создавайте тип для каждого сообщения.
6. По умолчанию логируйте окончательно обработанную ошибку на границе операции. Возврат и логирование одной ошибки на каждом слое создают дубли; отдельное событие восстановления может заслуживать своего лога.
7. Сообщение должно объяснять сбой, не раскрывая секретов. Начинайте обычную фразу со строчной буквы, без конечной точки; сохраняйте регистр собственных имён и технических идентификаторов.
8. Ожидаемые сбои представляйте через `error`. `panic` допустим для нарушения инварианта, после которого продолжение работы некорректно.
9. Используйте `recover` только на определённой границе изоляции с понятной политикой результата и состояния. Обязательно сохраняйте наблюдаемость сбоя.
10. Когда значимы несколько независимых ошибок, сохраняйте их, например через `errors.Join`. Ошибка cleanup не должна незаметно заменять исходную ошибку операции.

## Исключения

Ошибка необязательной cleanup-операции может быть проигнорирована с объяснением. Ошибки записи, flush и закрытия выходного файла могут означать потерю результата и требуют отдельного решения.

## При ревью

Проследите ошибку от возникновения до потребителя: сохраняется ли нужная классификация, понятна ли операция, нет ли ложного успеха или повторных логов. Для изменения владения ресурсом дополнительно прочитайте [safety.md](safety.md).
