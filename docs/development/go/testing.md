# Тесты

Применение: проверка изменённого поведения, написание и ревью тестов, диагностика нестабильности.

## Правила

1. Обязательно соблюдайте наборы тестов, build tags и команды из [AGENTS.md](../../../AGENTS.md). Выбирайте проверку по изменённому контракту и используемым внешним зависимостям.
2. Проверяйте наблюдаемое поведение: результат, значимый побочный эффект и ошибку. Вызовы внутренних helper-функций важны лишь когда их порядок или количество входит в контракт.
3. Для изменения поведения покрывайте значимые успешные, ошибочные и граничные пути. Для исправления бага добавляйте воспроизводящий сценарий, когда автоматическая проверка практична.
4. Обязательно обеспечивайте независимость теста от порядка запуска и состояния машины. Используйте `t.TempDir`, локальные fixtures и явные зависимости.
5. Cleanup должен завершать фоновые задачи и освобождать ресурсы даже после неуспешной проверки. Учитывайте порядок `t.Cleanup` и завершения context.
6. По умолчанию объединяйте однотипные случаи в таблицу с именованными `t.Run`. Сценарии с разной подготовкой могут быть отдельными тестами.
7. Применяйте `t.Parallel` только при независимых ресурсах. Изменение окружения процесса или общего состояния несовместимо с параллельной изоляцией.
8. Синхронизируйте конкурентные тесты по событиям. Реальный `time.Sleep` не доказывает готовность; таймаут служит пределом ожидания. Для подходящих сценариев времени и goroutine используйте `testing/synctest`.
9. Ошибку проверки относите к текущему subtest. `t.Fatal` и `require` вызывайте из его тестовой goroutine; из worker передавайте результат тесту.
10. Helper-функции, сообщающие ошибки теста, отмечайте `t.Helper`. Сообщение проверки должно показывать сценарий, полученное и ожидаемое значение.
11. Используйте небольшие fake-реализации на границах зависимостей. Проверяйте их предположения контрактными тестами с настоящей зависимостью, когда это существенно для корректности.
12. Для конкурентного кода проверяйте остановку и отсутствие утечек; `goleak` доступен для такой проверки. Исключения должны относиться к конкретному известному фону, а не скрывать все текущие goroutine.

## Исключения

`testify` доступен для assertions; стандартный `testing` также подходит. Покрытие строк помогает искать пробелы, но не задаёт самоцель. Генератор `gotests` создаёт заготовки: ожидаемое поведение и содержательные assertions задаёт автор теста. Команды инструментов — в [tools.md](tools.md).

## При ревью

Проверьте, упадёт ли тест при предполагаемом дефекте, изолирован ли он и проверяет ли изменённый контракт. Для конкурентного поведения сопоставьте сценарии с [concurrency.md](concurrency.md). Запускайте подходящие проверки из `AGENTS.md`; для гонок используйте `-race` на поддерживаемом окружении.
