# Автономная реализация OpenSpec change

Stepan выполняет готовый OpenSpec change последовательно в текущей локальной
ветке: контроллер выбирает следующие целые пункты `tasks.md`, запускает только
настроенные проверки, проводит ревью и создаёт локальные коммиты. Он не делает
push, pull request, merge или deployment и не создаёт worktree либо ветку.

Это руководство относится к implementation loop. Подготовка feature-документов
остаётся отдельным [flow `/feature`](feature-flow.md).

## Перед началом

Подготовьте change с `proposal.md`, `design.md`, его спецификациями и исходным
`tasks.md`. Работайте в обычном Git-репозитории на заранее созданной локальной
неосновной ветке. Для нового run рабочая копия должна быть чистой; Stepan не
откатывает уже существующую работу и не переключает ветки. Основную ветку задаёт    
проектный `main_branch`, либо Stepan берёт её из `refs/remotes/origin/HEAD`.
Detached HEAD и неизвестная основная ветка блокируют новый run.

Проверки и агенты исполняются только на машине, где запущен Stepan. Успешная
кросс-сборка подтверждает компиляцию целевой платформы, но не её runtime-приёмку.

| Среда запуска | Статус |
| --- | --- |
| Windows/amd64 | поддерживается нативно |
| macOS/arm64 | поддерживается нативно; runtime-приёмка выполняется на физическом Apple Silicon Mac |
| Другие OS/архитектуры, включая Linux и Intel Mac | не поддерживаются |

Для macOS/arm64 сборка без CGO с Windows является только кросс-проверкой:

```powershell
$env:GOOS = "darwin"
$env:GOARCH = "arm64"
$env:CGO_ENABLED = "0"
go build -o stepan-darwin-arm64 ./cmd/stepan
Remove-Item Env:GOOS, Env:GOARCH, Env:CGO_ENABLED
```

## `stepan bootstrap`

Запустите `stepan bootstrap` из корня нужного Git-репозитория. Можно явно
выбрать provider так же, как для обычного запуска:

```text
stepan bootstrap --agent codex
stepan bootstrap --agent claude --agent-cli-name corporate-claude
stepan bootstrap --agent nessy
```

Bootstrapper получает контекст проекта, CI, скриптов и несекретных настроек и
может запросить Explorer через контроллер. Он не запускает проверки. Если
профиль `bootstrapper` (по умолчанию `high`) ещё не определён, терминал попросит
provider, model и, при необходимости, reasoning для одной bootstrap-сессии.

Bootstrapper предлагает оба раздела `implementation`: пользовательский
`~/.stepan/settings.json` (на Windows `%USERPROFILE%\.stepan\settings.json`)
и проектный `.stepan/settings.json`. Stepan валидирует предложенную структуру,
показывает diff каждого изменяемого файла и записывает его только после `y` или
`yes`. Существующие внешние поля, включая авторизацию, сохраняются и не должны
включаться в предложение или diff. После сохранения bootstrap завершается: он не
создаёт и не продолжает implementation run.

Для Nessy токен по-прежнему задаёт пользователь в верхнеуровневом
`nessy.auth_token` домашнего settings-файла; подробности есть в
[разделе Nessy README](../README.md#nessy). Не помещайте токены, cookies или
другие credentials в `implementation`.

## JSON-конфигурация

Stepan читает ровно раздел `implementation` из обоих settings-файлов. Профили,
назначения ролей и отдельные пределы могут быть заданы на обоих уровнях; проект
имеет приоритет. Проектный профиль полностью заменяет одноимённый пользовательский,
а значение `null` удаляет унаследованный профиль. Поля `checks`,
`required_checks`, `rules_file` и `main_branch` допустимы только в проектном
файле.

Ни provider, ни model не имеют встроенного значения: у каждого используемого
профиля должны быть непустые `provider` и `model`. Замените примерные model на
модель, которую поддерживает выбранный provider. Буквальные JSON-примеры ниже
проверяются production-конфигурационным валидатором в тестах репозитория.

Пользовательский файл определяет общие профили и при желании пределы:

<!-- implementation-config-user-example:start -->
```json
{
  "implementation": {
    "profiles": {
      "low": { "provider": "codex", "model": "example-low-model" },
      "medium": { "provider": "codex", "model": "example-medium-model" },
      "high": { "provider": "codex", "model": "example-high-model" },
      "ultra": { "provider": "codex", "model": "example-ultra-model" }
    },
    "limits": {
      "agent_timeout_seconds": 1800
    }
  }
}
```
<!-- implementation-config-user-example:end -->

Проектный файл задаёт проверяемую ветку, правила и команды. `platforms` заменяет
всю `command` для OS/архитектуры хоста; поля варианта не наследуются из общей
команды. `GOOS`/`GOARCH` внутри `env` являются целью конкретной кросс-сборки и
не выбирают вариант `platforms`.

<!-- implementation-config-project-example:start -->
```json
{
  "implementation": {
    "roles": {
      "orchestrator": "medium",
      "briefer": "high",
      "implementer": "medium",
      "task_reviewer": "high",
      "explorer": "low",
      "final_reviewer": "ultra"
    },
    "main_branch": "main",
    "rules_file": ".stepan/rules/index.md",
    "checks": {
      "unit": {
        "kind": "tests",
        "command": {
          "program": "go",
          "args": ["test", "./..."]
        },
        "cwd": ".",
        "timeout_seconds": 600
      },
      "macos_compile": {
        "kind": "build",
        "platforms": {
          "windows/amd64": {
            "program": "go",
            "args": ["build", "-o", "stepan-darwin-arm64", "./cmd/stepan"],
            "env": {
              "GOOS": "darwin",
              "GOARCH": "arm64",
              "CGO_ENABLED": "0"
            }
          }
        },
        "timeout_seconds": 600
      }
    },
    "required_checks": ["unit"]
  }
}
```
<!-- implementation-config-project-example:end -->

Каждая проверка имеет `kind` (`build`, `lint`, `static_analysis` или `tests`),
прямо запускаемые `command.program` и `command.args`, необязательные `env`,
`cwd`, `timeout_seconds` и необязательные замены `platforms` по ключу
`os/arch`. Stepan не запускает shell: если нужен интерпретатор скрипта, укажите
его как `program`. stdin закрыт, терминал не передаётся, код выхода `0` означает
успех. `env` дополняет окружение только этой команды и не переходит к следующей.

`required_checks` — непустой проектный список в обязательном порядке. После
`implementation_ready` контроллер запускает весь этот список с первой проверки
до первой ошибки. Дополнительная проверка может отсутствовать в
`required_checks`: исполнитель запрашивает только её имя, а контроллер выполняет
имена строго в запрошенном порядке до первой ошибки. Ни произвольные команды,
ни фильтры тестов агент передать не может.

`cwd` по умолчанию равен корню репозитория; относительные `cwd` и `rules_file`
разрешаются от него. Абсолютные пути допустимы в пределах правил для rules-file.
`~`, `%NAME%`, `$NAME` и иные подстановки в путях не раскрываются.

Значения по умолчанию, если их не переопределили `limits`:

| Поле | Значение |
| --- | ---: |
| `review_rounds` | 3 |
| `required_check_attempts` | 3 на цикл приёмки |
| `checks_requested` | 5 на задание |
| `brief_clarifications` | 3 после первого брифа |
| `exploration_limit` | 10 на эпизод исходной роли |
| `technical_attempts` | 3 на одну операцию |
| `final_review_rounds` | 3 на run |
| `agent_timeout_seconds` | 1800 секунд |
| `explorer_characters` | 12000 Unicode-символов |
| `timeout_seconds` проверки | 600 секунд |

Стандартные профили ролей: orchestrator и implementer — `medium`; briefer и
task_reviewer — `high`; explorer — `low`; final_reviewer — `ultra`; bootstrapper
— `high`. Это имена назначений, а не встроенные модели: соответствующие профили
всё равно нужно определить.

## Правила проекта

`rules_file` необязателен, но при наличии это один Markdown-файл внутри
репозитория. Его каталог становится корнем правил. Перед стартом и каждым
`/resume` Stepan рекурсивно проверяет все Markdown-файлы на этом уровне и ниже,
включая локальные Markdown-ссылки и изображения. Markdown-цель обязана остаться
в папке правил; другая локальная цель — в репозитории. Выход через `..` или
символическую ссылку, недоступная цель и недоступный индекс блокируют start или
resume. Web-ссылки допустимы и не проверяются по сети.

Агент сначала получает только индекс `rules_file` и читает связанные документы
по необходимости. Снимок или версия правил не сохраняются: изменение только
содержимого допустимых правил не отменяет уже принятую приёмку, хотя на resume
правила вновь проверяются и новые чтения увидят их актуальный текст.

## Контекстные команды и жизненный цикл

При найденном незакрытом run обычный `stepan` показывает change, этап,
последнее действие, причину остановки и только доступные в контексте команды:

| Команда | Назначение |
| --- | --- |
| `/status` | показать краткий прогресс и последнее состояние без запуска агента или проверки |
| `/pause` | прервать активную операцию и сохранить возобновляемую паузу |
| `/resume` | явно продолжить paused run после сверки входов и полного обязательного набора |
| `/stop` | закрыть run, сохранив коммиты и незакоммиченную работу; это не успех |
| `/implement <change>` | контрактная команда создания нового run из готового change; в текущей production-композиции ещё не подключена для репозитория без сохранённого run |

Недоступная введённая вручную команда возвращает краткую причину и ничего не
делает. Во время агентского вызова или проверки доступны только релевантные
`/pause`, `/stop` и `/status`; на паузе — `/resume`, `/stop`, `/status`.

`/resume` никогда не происходит автоматически. Он перечитывает и валидирует
оба settings-файла, проверяет правила, сверяет ветку, рабочую копию и OpenSpec,
создаёт свежие agent-сессии и всегда выполняет полный `required_checks` с
первой команды. Этот набор не расходует попытки. Ошибка конфигурации, правила,
окружения или проверки оставляет run на паузе с диагностикой; Stepan не ослабляет
проверки и не меняет scope автоматически. Изменение команд лишает затронутую
приёмку актуальности; изменение только текста правил — нет.

## Журнал и восстановление

Данные каждого run находятся вне репозитория в
`~/.stepan/runs/<run-id>/` (на Windows — `%USERPROFILE%\.stepan\runs\<run-id>\`).
Там хранятся append-only JSONL-журнал событий, SQLite-представление текущего
состояния, версии брифов, полные stdout/stderr проверок и другие связанные
файлы. JSONL — источник восстановления: событие сохраняется до применения к
SQLite. SQLite можно восстановить из журнала; автоматической очистки run или
логов нет.

После сбоя Stepan лишь обнаруживает незакрытый run и ждёт `/resume`; он не
запускает агентов или проверки сам. Прежние provider-dialogues не нужны: при
восстановлении создаются новые сессии по сохранённым брифам, результатам и
состоянию. Попытка учитывается консервативно до внешнего действия, поэтому
неподтверждённый старт после аварии остаётся потраченной попыткой. Единственное
адресное исключение — `/resume` после паузы из-за лимита: сбрасывается только
счётчик, вызвавший эту паузу.

При необходимости ручного исправления сначала поставьте run на паузу. Пауза и
закрытие не делают общий Git rollback. Изменения за пределами полномочий
конкретного агента Stepan пытается восстановить относительно состояния перед
этим вызовом и записывает отдельный журнал нарушений; если происхождение или
безопасный откат не доказаны, run остаётся на паузе для решения пользователя.

## Архитектура и проверка

Документный flow находится в [`internal/flows/spec`](../internal/flows/spec),
а автономный цикл — в [`internal/flows/impl_loop`](../internal/flows/impl_loop).
Они независимы и используют общий [`internal/agentruntime`](../internal/agentruntime),
конфигурацию, хранилище запусков и платформенные компоненты. Исторический
baseline архитектуры обновлён в [ADR 0002](adr/0002-current-stack-and-architecture.md);
границы provider runtime — в [ADR 0004](adr/0004-claude-cli-runtime.md).

Для реальных provider smoke-проверок используйте отдельный
[ручной план](../openspec/changes/autonomous-implementation-loop/manual-test-plan.md).
Он остаётся `not_run`, пока пользователь не выполнит сценарии; fake-runtime
тесты не являются проверкой реального provider.
