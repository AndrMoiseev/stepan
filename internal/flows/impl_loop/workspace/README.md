# Управление рабочей копией

`Control` — контракт наблюдения за рабочей копией, сравнения снимков,
выборочного восстановления и получения diff для ревью. `RootFinder` находит
корень; `Repository` добавляет проверки перед новым запуском. `Committer` и
`CommitObserver` отвечают за создание коммита и чтение его результата.

- `git.Control` — рабочая реализация поверх `internal/git` и Git CLI.
  Контрактные тесты и проверки начального состояния запускаются с тегом
  `git_integration`.
- `testfs.New()` — файловая реализация для тестов оркестрации без внешних
  процессов. Наблюдает обычные файлы, сохраняет снимки в памяти и поддерживает
  выборочное восстановление, историю тестовых коммитов и текстовый diff.
  Не моделирует staging, ветки, symlink, submodule, ignore-правила, hooks
  и Git-фильтры. Object ID и формат diff отличаются от Git.
- `testfs.Directory` задаёт корень рабочей копии для тестов контроллера.

`git/TestWorkspaceConformance` запускает одинаковые проверки для обеих
реализаций: обнаружение изменений, выборочное восстановление с сохранением
остальных файлов, отказ при устаревшем снимке или небезопасной цели,
проверку сериализованного снимка, коммит, наблюдение результата и diff.
Это совместимость проверенного поведения обычных файлов, а не полная эмуляция Git.
Git-специфичные гарантии проверяются отдельно в `git` и `internal/git`.

В `impl_loop` Git CLI и операции `internal/git` разрешены только внутри
`workspace/git`. Для тестов оркестрации используйте `testfs`; интеграционные
сценарии hooks и индекса подключают Git-адаптер и `git/testfixture` под тегом
`git_integration`. Архитектурный тест проверяет прямые обращения и импорты.

Обе реализации зависят от контракта, но не от пакета `impl_loop`.
Импорт `testfs` в рабочий код запрещён правилами `arch-go.yml`.
Типы снимков и различий пока принадлежат `internal/git`: их также используют
хранилище и другие потребители. Этот модуль не меняет формат сохранённого состояния.
