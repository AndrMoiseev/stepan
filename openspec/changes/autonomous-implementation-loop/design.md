## Context

Дизайн согласованного поведения первой версии, обновлённый 2026-09-12. Мотивация находится в proposal.md. Нормативные требования и проверяемые сценарии зафиксированы в четырёх спецификациях этого change:

- [implementation-loop](specs/implementation-loop/spec.md) — последовательное выполнение, приёмка и завершение.
- [implementation-agent-control](specs/implementation-agent-control/spec.md) — роли, контекст, ответы и ограничения.
- [implementation-configuration](specs/implementation-configuration/spec.md) — настройки, профили и проверки.
- [implementation-run-state](specs/implementation-run-state/spec.md) — состояние, лимиты, остановки и восстановление.

Спецификация поведения завершена; реализация и tasks.md для реализации самого цикла не входят в эту фиксацию. Технические решения согласованы ниже; совместимость форматов хранения и усиление изоляции осознанно отложены.

В Stepan уже есть provider-neutral интерфейс internal/agentruntime, сессии авторов и ревьюеров, сохранение и восстановление документного flow. Текущая политика документного агента разрешает чтение workspace и запись в отдельный каталог артефактов; повторные ревью документов инициируются пользователем. Новый цикл требует самостоятельной оркестрации, изменения кода и запуска проверок. Новый цикл размещается в internal/flows/impl_loop; документный flow переносится в internal/flows/spec, общий agentruntime сохраняется.

Полнота OpenSpec не считается гарантированной. Агент на любом уровне должен явно сообщать о пробелах, требующих существенного решения, вместо молчаливого выбора поведения.

## Goals / Non-Goals

**Goals:**

- Контроллер управляет всеми переходами и запусками агентов; агентные ответы являются входами для решения контроллера, а не разрешением агенту самостоятельно выполнять следующий этап.
- Сборку и проверки, включая промежуточную обратную связь, выполняет только контроллер; у исполнителя нет произвольного выполнения команд.
- Бриф достаточен для реализации и ревью отдельной задачи без чтения полной спецификации этими ролями.
- Коммиты небольшие и осмысленные, проходят обязательные команды и ревью; изменения Git hooks проверяются отдельно по разделу 8.
- Прогресс, основания проверок и счётчики попыток переживают остановку процесса независимо от сохранности агентского диалога.

**Non-Goals:**

- Push, PR, merge, deployment, автоматический перенос запуска на другую машину.
- Параллельная реализация задач и отдельный worktree в первой версии.
- Гарантия математической полноты спецификации или корректности кода только на основании тестов либо агентского одобрения.
- Отдельный агент ревью декомпозиции до выполнения: идея сохранена на будущее, но не включена в первую версию.

## Decisions

### 1. Последовательный цикл и критерии завершения

Вход запуска — выбранное OpenSpec change с исходным планом задач в tasks.md и исходное состояние репозитория. Контекст полной спецификации включает применимые требования и решения change, его tasks.md и релевантные основные specs для понимания delta-изменений и сохраняемого поведения.

Первая версия начинает реализацию change с нуля либо продолжает собственный сохранённый запуск. Приём чужой частичной реализации не предусмотрен. После закрытия запуска из-за проблемы спецификации пользователь сам определяет новые границы изменения; новый цикл не наследует автоматически задачи закрытого запуска.

Исходный план выполнения — tasks.md выбранного OpenSpec change; отдельный план поверх него не создаётся. Агент-оркестратор первоначально извлекает структурированный список задач, сохраняя порядок и иерархию. Контроллер сохраняет этот список в машинно-читаемом учёте — источнике истины для исполнения. Брифер (автор брифов) получает полную спецификацию, задачи и актуальный прогресс, исследует код и выбирает объём очередного брифа. Связи задач с брифами и коммитами отражают выполнение; отдельная сверка покрытия требований брифером или оркестратором не проводится.

До первой задачи контроллер запускает весь обязательный набор сборки и проверок исходного состояния. Если набор не проходит, реализация приостанавливается, диагностика сохраняется и передаётся пользователю. Исправления существующих проблем не включаются в scope автоматически.

После первоначального извлечения tasks.md имеет информационную роль. Оркестратор сам редактирует его, отмечая выполненные задачи и отражая новые задачи исправлений. Контроллер не разбирает Markdown для сверки галочек и не использует их для переходов. Машинно-читаемое состояние меняет только контроллер, в том числе сохраняя структурированные записи новых задач от оркестратора. Отметки tasks.md включаются в коммит вместе с реализацией; сами по себе они не являются доказательством выполнения.

```text
OpenSpec (with tasks.md) + rules + config
                    |
                    v
         Extract tasks (orchestrator)
                    |
                    v
          Baseline command checks
                    |
                    +-- Failure --> User decision
                    |
                    v
        Select next block + brief <--------------+
                    |                            |
                    v                            |
                Implement <----------+           |
                    |                |           |
                    v                |           |
             Command checks ---------+           |
                    |                |           |
                    v                |           |
              Brief review ----------+           |
                    |                            |
                    v                            |
          Accepted, awaiting commit              |
                    |                            |
                    v                            |
        Update tasks.md (orchestrator)            |
                    |                            |
                    v                            |
       Commit + complete tasks -- More tasks ----+
                    |
                    v
          Final checks + full review
                    |
                    +-- Findings --> Append tasks+
                    |
                    v
                 Complete
```

Единицы выполнения — конечные пункты tasks.md, то есть задачи или подзадачи без дочерних пунктов. Родитель завершается, когда завершены все его дочерние задачи; отдельно второй раз эта работа не выполняется. Брифер выбирает одну или несколько целых конечных задач: следующий непрерывный блок в порядке исходного документа, без пропусков и перестановок. Он не делит пункты на части; частичных статусов нет. Контроллер проверяет, что идентификаторы в брифе образуют непустое начало оставшегося списка. Граф зависимостей не строится. Если следующую задачу нельзя выполнить в этом порядке даже вместе с последующими, действует эскалация проблемы исходного плана.

Перед каждым коммитом обязательны командные проверки и ревью по актуальному брифу. После изменения кода предыдущие результаты не считаются доказательством для нового состояния: перед фиксацией проверяется именно фиксируемый код. Коммит создаёт контроллер после прохождения условий, а не исполнитель по собственному решению.

После успешных проверок и ревью контроллер сохраняет состояние «принято, ожидает коммита», передаёт оркестратору принятые идентификаторы для обновления tasks.md и создаёт общий коммит. Штатные hooks и сверка фактически созданного состояния обрабатываются по разделу 8; изменивший содержимое hook требует повторной приёмки до завершения задания. Информационное обновление прогресса после приёмки не является изменением требований или кода и не запускает новый раунд ревью само по себе. Только после успешного коммита выбранные задачи становятся выполненными в машинном учёте; завершение родителей вычисляет контроллер. При сбое Git промежуточное состояние сохраняется: продолжение завершает фиксацию, а не повторно реализует задачи. Для неудачи обновления информационного tasks.md отдельные обходы, предупреждения или дополнительные условия в первой версии не вводятся.

Когда в машинном учёте не осталось незавершённых задач, контроллер сам запускает финальные проверки и ревью. Полноту реализации всех требований проверяет финальный ревьюер. Для завершения change нужны выполненные задачи, отсутствие неразрешённых вопросов и существенных замечаний, успешные обязательные команды на итоговом состоянии и положительное финальное ревью.

### 2. Бриф как контракт задачи

Бриф содержит:

- Идентификаторы одной или нескольких выбранных целых конечных задач в исходном порядке.

- Ожидаемый результат и наблюдаемое поведение после коммита.
- Применимые требования, критерии приёмки, сценарии и ссылки на исходные требования.
- Необходимые решения дизайна, ограничения, совместимость и сохраняемое поведение.
- Зависимости от уже выполненных задач и используемые интерфейсы.
- Границы задачи и явно отложенные части.
- Применимые обязательные правила проекта, доступные исполнителю и ревьюеру.

Исполнитель и ревьюер задачи получают одинаковую актуальную версию контракта; полная спецификация в их рабочий контекст не передаётся. Оба могут читать код напрямую и обращаться к Explorer. Ссылки на требования нужны для трассировки и эскалации, а не вместо необходимых подробностей в брифе.

Бриф версионируется отдельными Markdown-файлами. Брифер возвращает выбранные задачи и содержание, а контроллер проверяет выбор, назначает идентификатор и версию и формирует YAML frontmatter:

```markdown
---
assignment_id: assignment-007
version: 2
task_ids:
  - task-012
  - task-013
---

## Ожидаемый результат
...
```

Журнал ссылается на файл и его хеш. Метаданные формирует контроллер, а не агент. Версии брифа не означают сохранения снимков правил. После обновления исполнитель оценивает уже написанный код по новой версии; старое одобрение ревьюера теряет силу. Исследовательские заметки хранятся отдельно от требований, поскольку сведения о коде могут устаревать с каждым коммитом.

Альтернатива — дать ревьюеру задачи полную спецификацию — отклонена: это позволяло бы компенсировать недостаточность брифа только при ревью и нарушало бы ограничение контекста. Отдельная предварительная проверка декомпозиции отложена; в первой версии используются эскалация недостаточности брифа и финальное ревью полноты реализации.

### 3. Роли, сессии и Explorer

Роли цикла: оркестратор, брифер (автор брифов), исполнитель, ревьюер задания, Explorer и финальный ревьюер. Bootstrapper — отдельная роль подготовки конфигурации в режиме stepan bootstrap. Для оркестратора и bootstrapper также назначаются профили через конфигурацию ролей.

Оркестратор работает в одной сессии на весь запуск. Его контекст — пакет OpenSpec, машинный список задач, состояние запуска и краткие результаты этапов; исследование кода ему не требуется. Он извлекает исходные задачи, отражает принятый прогресс в tasks.md и добавляет задачи по замечаниям финального ревью. Следующую работу выбирает брифер, а не оркестратор. Детерминированные переходы, исправления, проверки, маршрутизация запросов, лимиты и коммиты остаются контроллеру; он не вызывает оркестратора для каждого раунда исправлений.

Работа с документами OpenSpec изолируется в отдельном модуле без общего интерфейса адаптеров спецификаций. Модуль обеспечивает доступ к документам и их версиям, но не определяет релевантность основных specs и не извлекает задачи специальным Markdown-парсером. Извлечение задач выполняет оркестратор; необходимый контекст требований для брифа определяет брифер, при необходимости исследуя документы через Explorer.

Для каждого задания на один бриф создаются новые сессии исполнителя и ревьюера. Внутри задания сессии продолжаются через исправления и обращения к Explorer; следующее задание получает новый контекст. После перезапуска всегда создаются новые сессии из актуального брифа и сохранённого состояния без восстановления provider-specific диалогов, включая сессию оркестратора.

Автор брифов также получает отдельную сессию на каждое задание: полную спецификацию, исходные задачи, актуальный машинный прогресс и разрешённые внутренние вопросы. Он сначала выбирает целые задачи для этого задания. Уточнения текущего брифа обрабатываются в той же сессии. Explorer получает новую сессию на каждый запрос с вопросом и необходимым контекстом, без автоматической передачи истории других исследований. Финальный ревьюер получает новую сессию на каждый раунд; состав его контекста определён в разделе 5.

Explorer входит в первую версию. Он отвечает на конкретные вопросы о коде, зависимостях и тестах, возвращая краткие выводы, ссылки на файлы и символы, подтверждённые факты и неизвестные. Его помощь уменьшает объём исследовательского контекста у других агентов, но не заменяет их прямое чтение существенного кода и самостоятельную проверку доказательств.

Объём текстового ответа Explorer ограничивается конфигурацией: по умолчанию 12000 символов Unicode. Превышение обрабатывается запросом сокращения в той же сессии и техническими попытками без молчаливого обрезания. Он отмечает опущенную информацию, если всё найденное не помещается; большие фрагменты кода исходный агент читает самостоятельно по ссылкам.

Все агенты запускаются исключительно контроллером. Агент возвращает запрос помощи; контроллер сохраняет его, приостанавливает исходного агента, запускает вспомогательную роль, получает результат и продолжает исходную сессию. Прямые запуски субагентов и прямое общение агентов не допускаются.

Исполнитель самостоятельно читает и редактирует код, тесты и файлы зависимостей в рамках брифа. Прямое выполнение команд, в том числе сборки и проверок, запрещено правилами роли. В первой версии используются доступные ограничения текущего контракта адаптеров, инструкции агенту и постпроверки; отсутствие строгого технического запрета не блокирует реализацию. Генерация кода относится к настроенной сборке. Git-операции выполняет контроллер на соответствующих этапах. Отдельный запрос command_requested и политика разрешения произвольных команд в первую версию не вводятся: для согласованных сценариев достаточно файловых изменений и checks_requested.

Полная спецификация, брифы, правила проекта, конфигурация Stepan, состояние запуска и служебные данные Git запрещены для прямой записи исполнителем. Ограничения обеспечиваются в пределах возможностей текущих адаптеров и дополняются инструкциями и постпроверками по Git; это не утверждение о полной изоляции. Брифы обновляет автор через контроллер по имеющимся основаниям полной спецификации; проблемы самой спецификации закрывают запуск для ручного решения пользователем. Состояние запуска и служебные данные Git изменяет только контроллер. Необходимость изменения защищённого файла исполнитель эскалирует контроллеру, а не самостоятельно меняет условия своей приёмки.

Explorer — конечный исполнитель: он не может ни запускать агентов, ни запрашивать их запуск через контроллер. Если данных недостаточно или обнаружена проблема, он возвращает её исходному агенту через контроллер. Контроллер явно отклоняет делегирование от Explorer. В первой версии один агент запрашивает одно исследование за раз.

#### Контракт адаптеров: запись в workspace

Контракт internal/agentruntime расширяется явным разрешением записи в workspace, которое контроллер задаёт при создании сессии. Workspace означает корневой каталог Git-репозитория и его подкаталоги независимо от того, отслеживаются ли файлы Git. Разрешение неизменно на протяжении сессии; по умолчанию workspace остаётся доступным только для чтения, сохраняя поведение существующих документных агентов.

Внешний ArtifactRoot сохраняется как отдельный каталог для артефактов. Разрешение записи в workspace не требует переносить ArtifactRoot внутрь проекта или использовать его вместо рабочего каталога. Существующий запрет размещения ArtifactRoot внутри workspace относится к каталогу артефактов и не должен запрещать новый режим редактирования проекта.

Контроллер включает запись в workspace для исполнителя и оркестратора. При этом исполнитель вправе менять только файлы в рамках брифа с установленными исключениями, а оркестратор — только tasks.md выбранного change. Для остальных ролей workspace остаётся доступным только для чтения. Разрешение записи само по себе не разрешает выполнение команд, делегирование, изменение служебных данных Git или других защищённых файлов. Адаптеры применяют доступные технические ограничения, а инструкции ролей и постпроверки контроллера ограничивают допустимые изменения согласно разделу об ограничениях первой версии.

Это расширение отделяет возможность редактировать проект от механизма временных черновиков документного flow. Альтернатива — разрешить размещение ArtifactRoot внутри workspace и использовать его как универсальное разрешение записи — отклонена: она смешивает назначение каталога артефактов с правами на рабочую копию. Строгая изоляция отдельных путей остаётся отдельным усилением защиты и не становится условием первой версии.

### 4. Существенные решения и эскалация

Исполнитель или ревьюер возвращает «бриф неполон или противоречив». Автор брифа разрешает вопрос по полной спецификации, если там есть однозначное основание, выпускает новую версию, и цикл продолжается. Если полная спецификация неполна или противоречива и требуется решение пользователя, контроллер сохраняет диагностику и закрывает запуск. Пользователь решает проблему вручную и сам определяет новые границы изменения для возможного нового цикла.

Наличие более широкого контекста не даёт права придумывать требования. Агент может предложить варианты и рекомендацию, но не утвердить существенное решение без основания. Существенны решения, затрагивающие:

- Наблюдаемое поведение и публичные интерфейсы.
- Данные, совместимость, scope и критерии приёмки.
- Производительность: задержки, пропускную способность, память, количество внешних запросов и связанные компромиссы.

Технические детали внутри согласованных ограничений остаются самостоятельными решениями исполнителя. Оптимизация, сохраняющая поведение и ограничения, допустима; неоговорённый компромисс, например устаревание данных ради кеширования, требует эскалации. Сомнение в существенности выбора тоже поднимается явно.

Эскалация указывает конкретный пробел или конфликт, основания, заблокированное действие и причину, по которой нельзя принять обычное техническое решение. Автоматическое обновление полной спецификации по ответу пользователя и продолжение закрытого запуска не предусмотрены. Уже созданные коммиты и незакоммиченная работа сохраняются без автоматического отката. Проблемы условий выполнения обрабатываются иначе — паузой согласно разделу 7.

Внутреннее уточнение брифа по неизменной полной спецификации приводит к переоценке незакоммиченной работы. Уже выполненные задачи сохраняют статус; обнаруженные на финальном ревью дефекты оформляются новыми задачами и исправляются новыми проверенными коммитами. История не переписывается. Изменение пользователем границ полной спецификации закрывает запуск.

### 5. Командные проверки и два уровня ревью

Обязательные команды задаются конфигурацией. Пользователь заполняет её сам либо отдельно просит Stepan подготовить вариант по CI, скриптам, настройкам инструментов и инструкциям репозитория и подтверждает результат. Исполнитель не ослабляет проверки автоматически ради успешного результата.

Граница защиты условий приёмки распространяется и на файлы, определяющие обязательные проверки, например Makefile, на который ссылается настроенная команда. Явного решения об изменении такого определения в полной спецификации, перенесённого в бриф, достаточно: отдельное подтверждение пользователя не требуется. Без этого основания необходимость изменения эскалируется. Это исключение не передаёт исполнителю управление состоянием запуска, служебными данными Git или исходной спецификацией. Отдельный процесс изменения проверок в первой версии не вводится; ожидается, что такие изменения обычно делаются вне цикла.

Базовая модель проверки: имя, вид (сборка, линтер, статический анализ, тесты), команда, рабочий каталог, таймаут и применимые платформы. Исходное правило успеха — код выхода 0; перечисленный применимый набор обязателен. Формат команды и платформенных вариантов определён в разделе 6. Сборка включает необходимую генерацию кода.

Все проверки запускает исключительно контроллер. Исполнитель знает каталог доступных проверок: имена, виды и назначение. Для промежуточной обратной связи он возвращает checks_requested с именами выбранных проверок из конфигурации. Произвольная команда или дополнительные параметры, например фильтр пакета или отдельного теста, в запросе не допускаются; каждая выбранная проверка выполняется целиком. Контроллер возвращает статус, диагностический вывод и сведения о проверенном состоянии кода, затем исполнитель продолжает ту же сессию. Перед коммитом контроллер независимо от промежуточных запросов запускает полный обязательный набор.

Контроллер централизованно планирует проверки и в первой версии выполняет их последовательно. Это сохраняет единую точку управления для будущей параллельной реализации: проверки в общем случае используют общие ресурсы и не могут произвольно запускаться одновременно. Проверка связана со стабильным состоянием кода; одной очереди команд недостаточно, если другие исполнители меняют проверяемые файлы. Конкретная изоляция будущей параллельности отложена вместе с самой параллельностью.

Обязательные проверки идут в проектном порядке, от дешёвых к дорогим; промежуточные — только в порядке запроса исполнителя. На первой ошибке контроллер прекращает набор; оставшиеся проверки отмечаются невыполненными. Диагностика передаётся исполнителю, кроме исходной проверки и набора при /resume: их неуспех сохраняет паузу для пользователя. Перед коммитом после исправлений обязательный набор начинается заново с первой проверки. Граф зависимостей проверок в первой версии не вводится.

Повторный запрос проверки без изменения кода допустим и расходует попытку. Все результаты сохраняются; последующий успех позволяет продолжить при соблюдении остальных условий приёмки, но не удаляет предыдущий сбой. Ревьюер задачи видит историю результатов и может потребовать разобраться с нестабильным тестом.

Сборка и проверки могут изменять файлы: например, генерировать код, форматировать его или обновлять lock-файлы. Контроллер определяет изменения после выполнения и передаёт их исполнителю как часть результата задачи. Такие изменения входят в проверяемый diff; изменение ранее одобренного кода делает одобрение устаревшим и требует нового ревью до коммита. Действует общее правило актуальности проверок для фиксируемого состояния, включая изменения, внесённые самими командами.

Проверки не служат обходом защиты файлов. Неожиданное изменение защищённого файла, не предусмотренное явным решением спецификации и брифом, приостанавливает цикл для решения пользователя. Если генерация меняет код при каждом запуске и не позволяет получить устойчивый проверенный результат, повторы ограничиваются существующими лимитами, затем проблема возвращается как execution_blocked с диагностикой. Автоматическое исключение таких файлов из проверяемого diff не допускается.

Если обязательную проверку невозможно выполнить, она не становится пройденной. Ручная и межмашинная приёмка находятся вне цикла первой версии; локальный результат явно указывает платформу автоматических проверок.

После неуспешной проверки в активном задании контроллер передаёт исполнителю результат и диагностику. Исходный набор и набор при /resume вместо этого оставляют запуск на паузе для пользователя. Если причина в реализации задачи, исполнитель исправляет код и повторно запрашивает проверку; попытки учитываются в лимитах. Существенное решение или недостаточность брифа требуют clarification_required. Проблемы окружения либо конфигурации проверки, препятствующие выполнению, сообщаются через execution_blocked: контроллер сохраняет состояние, приостанавливает зависимую работу и передаёт проблему пользователю. Проверка остаётся непройденной; исполнитель не может отключить её или объявить успешной на основании собственного объяснения.

Существующие тесты можно изменять, если это следует из брифа. Ревьюер проверяет основание нового ожидаемого поведения и сохранение или замену необходимого покрытия. Удаление, отключение тестов или ослабление утверждений только ради успешных проверок блокирует коммит. Если тест противоречит брифу, но бриф не объясняет изменение прежнего поведения, исполнитель запрашивает уточнение.

При наличии ссылки на правила работы с кодом они обязательны и для исполнителя, и для ревьюеров. Недоступность указанного файла блокирует подготовку. Нарушение явного правила, в том числе стилистического, может блокировать коммит; предпочтения ревьюера сверх правил не блокируют. Блокирующее замечание указывает основание и место нарушения.

Ревью задачи проверяет актуальный бриф, правила, diff и результаты проверок, включая дефекты и влияние на существующее поведение. Оно не заменяет командные проверки, а их успех не доказывает полноту реализации. Незафиксированное существенное допущение препятствует одобрению.

Diff задачи охватывает всё состояние от последнего принятого коммита (для первой задачи — исходного коммита запуска), включая новые файлы и изменения генерации. На повторных раундах ревьюер видит весь актуальный diff задачи и предыдущие замечания; история обсуждения сохраняется в сессии задачи.

Исполнитель может оспорить замечание через review_disputed: указать его устойчивый идентификатор, аргументы и подтверждающие ссылки на код, бриф или результаты проверок. Контроллер передаёт возражение ревьюеру в существующую сессию. Ревьюер либо снимает замечание с обоснованием, либо сохраняет его, отвечая на аргументы. Неоднозначность брифа эскалируется автору брифа. Исполнитель не может самостоятельно закрыть замечание; до разрешения блокирующего замечания коммит не создаётся. Обмен возражениями расходует лимит раундов задачи.

Финальный ревьюер в каждом новом раунде получает только актуальную полную спецификацию, правила проекта и совокупный итоговый diff от исходной точки ветки. История реализации, предыдущие замечания, история исправлений и результаты командных проверок в его входной контекст не включаются; проверки отдельно учитывает контроллер. Ревьюер может исследовать окружающий код напрямую и через Explorer. Он проверяет полноту реализации всех требований и взаимодействие частей. Замечания поступают оркестратору: тот возвращает структурированные новые задачи со ссылками на замечания для добавления контроллером в конец машинного списка и отражает их в конце tasks.md. Брифер затем выбирает следующий непрерывный блок в обычном порядке. Уже выполненные задачи не открываются заново. Если требования однозначны, добавление исправлений автономно; проблема полной спецификации, требующая пользователя, закрывает запуск. После исправлений итоговые проверки и финальное ревью повторяются.

### 6. Конфигурация, команды и правила

Используется JSON: ~/.stepan/settings.json на пользовательском уровне и <repo>/.stepan/settings.json в Git на проектном. Настройки цикла находятся в implementation; существующая авторизация Nessy остаётся в своём разделе. Состояние запусков хранится отдельно.

| Настройка | Уровень |
|---|---|
| checks, required_checks, rules_file, main_branch | Только проект |
| profiles, roles, limits, таймаут агента и объём ответа Explorer | Пользовательский и проектный |

Пользовательские значения задают базу; проект заменяет явно заданные назначения ролей и отдельные лимиты. Одноимённые профили заменяются целиком, null удаляет унаследованный профиль; ссылки на удалённый или отсутствующий профиль вызывают ошибку. Для проверок наследования и null-удаления нет. Проектные поля в пользовательском implementation считаются ошибкой.

Модели не зашиваются в приложение. Профили low, medium, high и ultra задают provider, model и reasoning, где он применим. Название профиля не является reasoning. Неподдерживаемый явно заданный reasoning не игнорируется. Распределение ролей по умолчанию:

| Роль | Профиль |
|---|---|
| Оркестратор | medium |
| Брифер | high |
| Исполнитель | medium |
| Ревьюер задания | high |
| Explorer | low |
| Финальный ревьюер | ultra |
| Bootstrapper | high |

Перед реализацией проверяются все роли цикла, их профили, параметры и наличие назначенных агентских программ. Установка всех трёх провайдеров не обязательна, если используются не все; поддержка Codex, Claude и Nessy входит в объём первой версии. Bootstrapper проверяется отдельно при входе в свой режим.

#### Формат проверок

Команды запускаются напрямую через program и args. Shell возможен как явно выбранная программа, например pwsh с ["-NoProfile", "-File", "scripts/check.ps1"] или bash с ["scripts/check.sh"]. Неявного shell нет. Команда наследует окружение процесса Stepan, env переопределяет значения только для неё. Проверки выполняются без терминала и с закрытым stdin; успех — код 0.

Пример проектного раздела:

```json
{
  "implementation": {
    "checks": {
      "build": {
        "kind": "build",
        "command": {
          "program": "go",
          "args": ["build", "-o", "stepan", "./cmd/stepan"]
        },
        "platforms": {
          "windows/amd64": {
            "program": "go",
            "args": ["build", "-o", "stepan.exe", "./cmd/stepan"]
          }
        },
        "cwd": ".",
        "timeout_seconds": 600
      },
      "tests": {
        "kind": "tests",
        "command": {
          "program": "go",
          "args": ["test", "./..."],
          "env": { "CGO_ENABLED": "0" }
        },
        "cwd": ".",
        "timeout_seconds": 600
      }
    },
    "required_checks": ["build", "tests"]
  }
}
```

Виды включают build, lint, static_analysis и tests. Генерация входит в сборку. Вариант platforms выбирается по ОС/архитектуре машины Stepan, например windows/amd64 или darwin/arm64, и целиком заменяет command. При отсутствии варианта используется общий command; если нет и его, обязательная проверка блокирует подготовку. Дополнительная проверка без подходящей команды не выполняется по запросу с неподходящими настройками. Никакого молчаливого пропуска обязательной проверки нет. Кросс-сборка — отдельное имя с целевыми GOOS/GOARCH в env, не влияющими на выбор варианта для машины запуска.

required_checks непуст и задаётся только проектом. checks может содержать дополнительные проверки для быстрой обратной связи. checks_requested выполняет только запрошенные имена в порядке исполнителя до первой ошибки; implementation_ready независимо запускает весь required_checks в проектном порядке до первой ошибки. Смешанный запрос не переставляется по обязательному списку.

cwd по умолчанию — корень репозитория; относительный cwd и rules_file считаются от корня, абсолютные пути допускаются при соблюдении границ правил. Раскрытия ~ или переменных окружения в путях нет. Определения проверок и rules_file не имеют пользовательского уровня.

Таймаут одной проверки по умолчанию 600 секунд, задаётся в её определении. При превышении контроллер завершает команду и дочерние процессы и сохраняет неуспех. Ручные проверки и межмашинная приёмка в цикл первой версии не входят. Итог показывает фактическую платформу; кросс-компиляция не объявляется runtime-проверкой целевой ОС.

#### Правила

rules_file — одна необязательная ссылка на Markdown (.md), обычно индекс. Каталог файла является корнем всех правил и находится внутри репозитория. До старта и при каждом /resume контроллер рекурсивно сканирует файлы этого каталога и ниже. В Markdown проверяются локальные ссылки и изображения: .md-цели должны оставаться внутри папки правил; остальные локальные цели — внутри репозитория. Проверка учитывает .. и символические ссылки; отсутствующие локальные цели или выход за границу блокируют подготовку/продолжение с диагностикой. Веб-ссылки разрешены без сетевой проверки.

Локальные ссылки внутри Markdown разрешаются относительно каталога содержащего их документа. Механический обход не меняет progressive disclosure для агента: в стартовый контекст включается только индекс, связанные документы читаются по необходимости. Дополнительные внешние корни чтения для правил не вводятся. Снимки и версии правил не сохраняются, изменение их содержимого не запускает повторную приёмку само по себе. Новое чтение получает актуальный файл; старая сессия может помнить прежнее содержание.

#### Применение настроек

Активная конфигурация фиксируется для текущего периода выполнения. Каждый /resume перечитывает, проверяет и принимает актуальные настройки без /reload-config и дополнительного подтверждения, сохраняя изменения эффективной конфигурации в журнале. Некорректные настройки оставляют запуск на паузе. Смена профиля создаёт новую сессию соответствующей роли, но не сбрасывает счётчики. Изменения команд лишают затронутую приёмку актуальности; правила исключены из версионирования. Полный обязательный набор при каждом /resume описан в разделе 8.

### 7. Лимиты конкретных циклов и остановки

Общий бюджет агентских вызовов задания не вводится. Ограничиваются конкретные циклы:

| Счётчик | По умолчанию | Область |
|---|---:|---|
| Ревью задания | 3 | Первичное и повторные рассмотрения задания, включая возражения |
| Обязательный набор | 3 | Один цикл приёмки до успеха; исправление упавшей проверки не сбрасывает цикл |
| checks_requested | 5 | Запросы на задание, независимо от числа команд и результата |
| Уточнение брифа | 3 | После первоначальной выдачи, на всё задание |
| Explorer | 10 | Один эпизод работы исходного агента, включая bootstrapper |
| Технические попытки | 3 | Одна операция, включая первоначальный вызов |
| Финальное ревью | 3 | Весь запуск, включая первичный раунд |

Успешный обязательный набор завершает свой цикл; изменения по ревью открывают новый цикл проверок с полным пределом. Продолжение исходного агента после Explorer не создаёт новый эпизод; его результат или переход к следующему этапу завершает эпизод. Техническое исправление ответа и повтор после отката запрещённых правок относятся к той же операции и техническому счётчику, не создавая ещё один семантический раунд. Самостоятельная следующая операция получает новый технический счётчик.

Первое выполнение входит в соответствующий лимит. Первоначальная выдача брифа не входит в цикл его уточнений. Начало попытки записывается устойчиво до вызова агента/команды; после аварии записанная попытка считается потраченной даже при неопределённости фактического старта. Прерванная обычная проверка расходует попытку и не получает успешного результата. Исключение — полный набор при каждом /resume: он не расходует попытки.

Идентификатор задания и незавершённые счётчики сохраняются при пересмотре брифа, смене профиля и перезапуске. Нельзя получить новый запас простым обращением за помощью. Когда требуется выполнение сверх предела, контроллер сохраняет причину и ставит паузу; успешный последний допустимый раунд не вызывает паузу сам по себе. Явное продолжение сбрасывает только счётчик, вызвавший лимитную паузу, сохраняя историю. Другой исчерпанный предел не обходится этой командой. Автоматического повышения профиля и восстановления лимитов нет.

Таймаут агентского вызова — 1800 секунд по умолчанию, включая его инструменты; превышение прерывает вызов и обрабатывается техническими попытками. Объём текстового ответа Explorer — 12000 символов Unicode по умолчанию. Превышение вызывает запрос сокращения в той же сессии с техническим учётом, без молчаливого обрезания.

| Причина остановки | Последствие |
|---|---|
| Разрешимый по полной спецификации пробел брифа | Уточнение в пределах лимита |
| Существенная проблема полной спецификации | Закрытие запуска |
| Окружение, конфигурация, execution_blocked, неизвестные изменения | Пауза |
| Следующий раунд превысит лимит | Пауза; адресный сброс по продолжению |
| Пользовательская пауза | Прерывание работы с возможностью продолжения |
| Пользовательский /stop | Закрытие без объявления успеха |

Пауза и закрытие сохраняют коммиты и незакоммиченную работу. Отдельное правило отката выявленных запрещённых изменений агента сохраняется.

### 8. Рабочая копия, журнал и восстановление

Ветка подготовлена пользователем, чистая перед новым запуском; worktree, создание и переключение веток не используются. Основная ветка и detached HEAD запрещены. main_branch берётся только из проекта; при отсутствии используется локальный refs/remotes/origin/HEAD, неизвестное имя требует настройки.

На рабочую копию допускается один незакрытый запуск, включая паузу. Новый начинается после завершения или закрытия прежнего. Блокировка ОС допускает один управляющий процесс; второй может читать статус. Блокировка освобождается при завершении процесса; разные репозитории работают независимо. Ручное редактирование разрешено на паузе. Перед следующей операцией сверяются отпечаток файлов, HEAD и индекс; неизвестное изменение вызывает паузу. Проверка перед коммитом и сверка результата после него дополняют блокировку. Это не строгая защита от сторонних редакторов и Git.

#### Источник истины и файлы

Каталог ~/.stepan/runs/<run-id>/ содержит прикладной журнал событий JSONL, текущее представление состояния SQLite и связанные файлы. JSONL — источник восстановления БД, а не экспорт после записи в SQLite и не внутренний WAL SQLite.

Порядок:
1. Присвоить событию последовательный номер, добавить строку JSONL и принудительно сохранить на диск.
2. Применить событие в транзакции SQLite вместе с номером последнего применённого события.
3. После сбоя применить отсутствующие события однократно; при потере БД воспроизвести весь журнал.

Незавершённая последняя строка после аварии отбрасывается; повреждение внутри журнала требует остановки с диагностикой. Большие результаты сохраняются отдельными файлами до публикации ссылки на них в журнале. Полное восстановление требует журнал и связанные файлы. Каталог хранится бессрочно до явного удаления пользователем, включая закрытые запуски.

В журнале и состоянии учитываются репозиторий, рабочая копия, ветка и исходный коммит; исходные документы OpenSpec и их версии; задачи, задания, брифы и коммиты; принятые конфигурации и фактические профили; вызовы, результаты, открытые вопросы, проверки и основания приёмки; счётчики циклов, остановки, нарушения и решения пользователя. Галочки tasks.md и история провайдерских диалогов не являются источником переходов. Версии и снимки правил исключены.

Версионирование формата, совместимость и миграции откладываются до первой относительно стабильной версии цикла. База для восстановления — идентификаторы, порядок событий и воспроизведение в текущей реализации. Продолжение старых запусков после изменения формата во время отладки не гарантируется.

#### Коммит и окно сбоя

Внешние операции имеют записи о начале и результате. До создания коммита сохраняются ожидаемые родитель, дерево, сообщение и идентификатор операции. Содержательное сообщение готовит исполнитель в implementation_ready и обновляет после исправлений; контроллер проверяет непустоту и добавляет:

```text
Stepan-Run: <run-id>
Stepan-Assignment: <assignment-id>
Stepan-Operation: <operation-id>
```

При восстановлении контроллер сопоставляет служебные строки, родителя, дерево и сообщение с фактическим Git. Созданный коммит завершает учёт без дублирования; неоднозначность вызывает паузу. Принятое задание до успешного коммита остаётся ожидающим фиксации.

Git hooks не отключаются. Их отказ сохраняет ожидание коммита и вызывает паузу с диагностикой. После коммита сверяется фактическое дерево и оставленная рабочая копия. Если hook изменил содержимое, задача не завершается по старой приёмке: требуется повторная приёмка фактического состояния. Созданный коммит не переписывается, необходимые исправления проходят цикл и новый коммит.

#### Продолжение

После перезапуска Stepan показывает найденный незакрытый запуск текущей рабочей копии: change, этап, последнее действие и причину остановки. Агенты и проверки не запускаются до /resume, run-id вводить не нужно. Восстановление всегда создаёт новые агентские сессии из брифов, результатов и состояния, включая оркестратора; provider-specific resume диалогов не используется. В работающем процессе сохраняются согласованные сессии.

Каждый /resume, в том числе после обычной паузы:
1. Сверяет Git и состояние, проверяет спецификацию и допустимые ручные изменения; изменение требований, требующее нового scope, закрывает запуск.
2. Перечитывает и проверяет актуальную конфигурацию, проверяет папку правил; изменения конфигурации сохраняются без отдельного подтверждения.
3. Запускает весь обязательный набор с первой команды до первой ошибки без расхода попыток.
4. При неуспехе остаётся на паузе с диагностикой без автоматических исправлений; при успехе продолжает работу, повторяя ревью, если код, спецификация или команды лишили его актуальности.

Прежние потраченные попытки сохраняются, кроме адресного сброса причины лимитной паузы. Восстановительный набор не повторяет только прерванную команду и не расходует счётчики. Изменение содержимого правил само по себе не аннулирует результаты.

### 9. Исходный контракт ответов контроллеру

Для каждой роли используется отдельная схема ответа с kind. Контроллер сам привязывает результат к вызову, заданию и версиям входов; агент не повторяет служебные идентификаторы. Для совместимости транспорта применяются object-схемы без oneOf, все properties перечисляются в required, семантически отсутствующие данные передаются пустыми transport-placeholder значениями и нормализуются до доменного слоя. Недопустимый kind, схема или данные запускают техническое исправление.

plan_ready исключён: план задач уже входит во входной пакет OpenSpec. Оркестратор возвращает первоначальный структурированный список, затем новые задачи по финальным замечаниям и результат отражения прогресса в tasks.md. Их конкретные транспортные имена задаются в схемах роли при реализации; это локальные имена, не отдельный пользовательский контракт. Они не включают выбор следующей работы или решение о завершении задания: первое делает брифер, второе — контроллер по фактам приёмки и коммита. Контроллер проверяет структуру, уникальность идентификаторов и допустимость переходов машинного учёта, но не сверяет смысл или галочки Markdown.

| Ответ | Роль | Реакция контроллера |
|---|---|---|
| brief_ready | Брифер | Проверить, что выбран непустой начальный блок оставшихся конечных задач без пропусков; сохранить бриф и запустить исполнителя |
| implementation_ready | Исполнитель | Запустить обязательные команды |
| checks_requested | Исполнитель | Выполнить только запрошенные проверки в порядке исполнителя до первой ошибки и вернуть результаты |
| review_passed | Ревьюер задачи или финальный ревьюер | Проверить остальные условия коммита или завершения |
| changes_requested | Ревьюер задания или финальный ревьюер | Передать замечания исполнителю либо оркестратору для добавления задач соответственно |
| review_disputed | Исполнитель | Передать аргументированное возражение ревьюеру в существующую сессию |
| execution_blocked | Агент, обнаруживший препятствие выполнения | Сохранить диагностику, приостановить зависимую работу и передать проблему пользователю |
| exploration_requested | Брифер, исполнитель, ревьюер задания, финальный ревьюер или bootstrapper | Выполнить исследование и продолжить исходную сессию |
| exploration_result | Explorer | Вернуть результаты исходному агенту |
| clarification_required | Любая роль | Уточнить бриф внутри цикла; при необходимости решения пользователя по полной спецификации закрыть запуск; Explorer возвращает проблему исходному агенту |

implementation_ready не означает завершения задачи. review_passed не разрешает коммит при непройденных командах, устаревших входах или открытых вопросах.

checks_requested означает промежуточную проверку и возврат управления исполнителю, а implementation_ready начинает обязательную приёмку перед коммитом с полным набором, определяемым контроллером. Запрос checks_requested содержит только имена проверок из конфигурации; служебную привязку к заданию формирует контроллер; команды и параметры выполнения из ответа агента не принимаются. Контроллер проверяет существование имён и допустимость запроса для текущего состояния. command_requested не входит в контракт.

Запрос Explorer содержит вопрос, контекст, границы исследования и уже известные факты. Эскалация содержит пробел/противоречие, ссылки на основания, заблокированное решение и его существенность, варианты и рекомендацию при наличии. Замечания ревью содержат устойчивый идентификатор, проблему, место, основание и ожидаемый результат исправления.

execution_blocked содержит описание заблокированного действия, подтверждающую диагностику, предпринятые попытки и необходимое действие пользователя. Этот ответ относится к условиям выполнения; clarification_required относится к пробелам или противоречиям требований. review_disputed содержит идентификатор замечания, аргументы и подтверждающие ссылки; его обработка не обходит лимиты или блокировку коммита.

Один ответ означает одно следующее действие: результат, запрос исследования или проверок либо вопрос. Контроллер проверяет допустимость ответа для роли и состояния и связывает его с конкретным заданием и версиями входов. Запрос исследования или проверок завершает текущий вызов, сохраняя возможность продолжения исходной сессии. При восстановлении различаются выполненные и прерванные запросы.

Падения процесса, таймауты, некорректные структурированные ответы и неуспешные команды фиксируются контроллером как отдельные события выполнения. Недоступность окружения не маскируется как недостаточность спецификации.

## Risks / Trade-offs

### Ограничения ролей и реакция на нарушения в первой версии

Для всех ролей применяются ограничения, доступные в текущем контракте адаптеров агентов, инструкции и проверка состояния Git после вызова. Обязательное усиление адаптеров до строгой изоляции не входит в условия реализации первой версии. Для оркестратора разрешённая запись ограничена tasks.md выбранного change; машинно-читаемое состояние он не изменяет напрямую.

Перед вызовом контроллер сохраняет состояние, достаточное для сравнения и восстановления файлов после этого вызова. Проверяется именно разница за вызов, а не весь diff относительно HEAD: рабочая копия может уже содержать правомерные незакоммиченные изменения исполнителя или генерации.

При обнаружении несанкционированных изменений, внесённых агентом, контроллер откатывает только эти изменения к состоянию до вызова и записывает случай в отдельный журнал нарушений. Правомерная ранее сделанная работа сохраняется; общий reset рабочей копии недопустим. В журнале сохраняются роль и вызов, затронутые пути, нарушенное ограничение и результат отката. После успешного отката ответ вызова не принимается как успешный результат: агенту передаётся диагностика и вызов повторяется в пределах технического лимита, сохраняя разрешённые изменения. Само нарушение не требует отдельного подтверждения или паузы, пока допустим технический повтор.

Это правило отличается от обнаружения внешних изменений неизвестного происхождения: они не считаются автоматически действиями агента и не откатываются по этому основанию. Если безопасно отделить или восстановить изменения нельзя, это препятствие выполнения, для которого действует execution_blocked. Обычная пауза или закрытие запуска по-прежнему сохраняет работу; откат относится только к выявленным несанкционированным изменениям агента.

### Открытые вопросы безопасности — не блокируют первую версию

Эти вопросы записаны отдельно для последующего усиления защиты. Отсутствие решения или строгой гарантии не является блокером реализации первой версии; принятый минимум — текущие возможности адаптеров, инструкции, постпроверки, локальный откат обнаруженных нарушений и журнал.

- Строгое ограничение путей записи и запрет обхода контроллера средствами каждого provider/runtime.
- Обнаружение запуска запрещённых команд и самостоятельного делегирования: проверка Git не доказывает, что таких действий не было.
- Действия вне наблюдаемой рабочей копии, сеть и другие побочные эффекты, которые невозможно восстановить откатом файлов.
- Охват новых, удалённых, игнорируемых файлов, символьных ссылок и служебных данных Git при сравнении и восстановлении.
- Надёжное отделение действий агента от одновременного внешнего редактирования и защита состояния между вызовом, проверкой и откатом.
- Защита самого состояния запуска и журнала нарушений от агента; формат, срок хранения и детализация отдельного журнала.
- Определение файлов, косвенно задающих обязательные проверки, и применение разрешённых спецификацией исключений.

### Остальные риски

- Пропуск требования в исходных задачах может дать согласованно неверную реализацию и локальное ревью: самодостаточные брифы, эскалация и финальное ревью полноты снижают риск, но не устраняют его полностью.
- Более простая модель исполнителя может не справиться даже с хорошим брифом: профили позволяют менять модель; гипотеза об экономии требует проверки на реальных задачах.
- Explorer может потерять детали при пересказе: нужны ссылки и неизвестные; исполнителю и ревьюеру остаётся прямое чтение кода.
- Изменение кода, спецификации, брифа или команд делает затронутые доказательства устаревшими; правила не версионируются и их изменение само по себе не аннулирует приёмку.
- Отсутствие worktree повышает риск вмешательства в рабочую копию: чистый старт и обнаружение неизвестных изменений перед продолжением/коммитом.
- Сбой между внешним действием и записью состояния может привести к повторению действия: используются JSONL до SQLite, события начала/результата и сопоставление Git-коммита с ожидаемыми данными.
- Многоуровневые исправления могут зациклиться: конкретные циклы имеют независимые лимиты с устойчивым учётом; общего бюджета задания нет.

### Осознанные ограничения отладки

Совместимость форматов сохранённых запусков и миграции откладываются до стабилизации цикла. Правила читаются в актуальном виде без снимков, поэтому контекст старой сессии может отличаться от нового чтения. Полный набор при /resume не расходует попытки, но при неуспехе требует ручного решения, в том числе если на паузе оставлен незавершённый код.

## Migration Plan

Сначала отдельным механическим шагом переносится internal/specflow в internal/flows/spec с обновлением импортов и архитектурных проверок. Поведение документного flow при переносе сохраняется. Затем добавляется internal/flows/impl_loop с именем Go-пакета impl_loop. Flow не зависят друг от друга; общий agentruntime и инфраструктурные компоненты остаются вне flows.

Контроллер impl_loop управляет заданиями, переходами, приёмкой и восстановлением. Работа с документами OpenSpec, хранение запусков и выполнение проверок выделяются в отдельные компоненты. Существующие Git-снимки и управление процессами оцениваются для повторного использования; доменные состояния specflow не становятся состояниями нового цикла. Общий контракт записи в workspace реализуется для Codex, Claude и Nessy с сохранением режима чтения по умолчанию.

Внедрение проверяется по нормативным сценариям четырёх specs, включая сбои между журналом, SQLite и Git, лимиты, восстановление, одинаковое поведение адаптеров и платформенные команды. Поддерживаемые сборки Windows/amd64 и macOS/arm64 сохраняются; выбор SQLite-драйвера должен учитывать кросс-сборку без CGO. Ручная runtime-приёмка самого Stepan на Mac остаётся процессом проекта, не ручной проверкой внутри автономного цикла.

Текущая фиксация обновляет только proposal, design и четыре specs. tasks.md для реализации подготавливается следующим этапом; импорт старого документного состояния и чужой частичной реализации не требуется.

## Implementation Details

### Контекст, ответы и большие результаты

Стартовое сообщение содержит весь обязательный контекст роли. Исполнитель и ревьюер получают полный одинаковый бриф, инструкции и входной файл правил; связанные правила и код читаются по необходимости. Продолжения несут новые результаты и изменения контекста; новая сессия после восстановления получает полный актуальный контекст и состояние. Полная спецификация исполнителю и ревьюеру задания не передаётся. Финальный ревьюер сохраняет независимый контекст из раздела 5.

Полные stdout/stderr команд сохраняются файлами в каталоге запуска. Агент получает имя проверки, команду, код завершения, длительность и до 20000 символов Unicode суммарного вывода. Для больших результатов передаются начало и конец с явной отметкой пропуска и ссылками на полные файлы. Файлы доступны роли для чтения, но не для изменения машинного состояния. Ссылки на эти файлы согласуются с существующим внешним каталогом артефактов и доступными ограничениями адаптеров.

### Интерактивный цикл и bootstrap

Основной режим использует /implement <change>, /pause, /resume, /stop и /status. Меню показывает только допустимые команды текущего состояния; ручной ввод недопустимой команды даёт короткое объяснение. Во время работы отображаются роль/проверка, задание, этап, длительность и счётчики; после ответа — краткий результат, запрос или причина остановки. Внутренние потоки инструментов агентов не выводятся в основной интерфейс. Проверки показывают имя команды, итог и ссылку на лог. История закрытых запусков хранится в файлах без отдельного меню выбора. Неинтерактивный режим реализации отложен.

stepan bootstrap — отдельный редкий режим по текущему репозиторию, без команды в меню задач. Bootstrapper имеет новую сессию на запуск режима, профиль high по умолчанию и доступ к Explorer через контроллер с лимитом 10 исследований на эпизод. Если профиль не настроен, до первого вызова пользователь выбирает provider, model и reasoning при необходимости.

Роль читает проект, CI, скрипты и доступные настройки и возвращает предложения по обоим уровням конфигурации с пояснениями. Контроллер проверяет предложения, показывает diff каждого файла и сохраняет после подтверждения. Существующая авторизация сохраняется, не передаётся агенту и не раскрывается в diff. Bootstrapper не запускает проверки самостоятельно. После сохранения режим завершается без старта реализации. Этот явный выбор при bootstrap отличается от автоматического перечитывания настроек по /resume уже существующего запуска.

### Отложенные решения

Блокирующих вопросов поведения перед реализацией не осталось. Совместимость и миграции форматов хранения, строгая изоляция из секции безопасности и отдельное предварительное ревью декомпозиции осознанно отложены. Конкретные имена внутренних типов, поля транспортных DTO и выбор библиотек определяются при реализации в рамках согласованных контрактов.
