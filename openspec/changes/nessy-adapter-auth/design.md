## Context

Мотивация и границы изменения описаны в `proposal.md`; пользовательские контракты — в `specs/nessy-adapter/spec.md` и `specs/nessy-auth/spec.md`.

Текущая точка сборки — `cmd/stepan/main.go`: `parseAgentConfig` выбирает провайдера, `prepareAgentLogin` запускает интерактивный Nessy для сочетания `qwen` / `nessy`, а `runtimeFactoryWithStarters` создаёт runtime. Отдельного загрузчика пользовательских настроек здесь нет.

`internal/agentruntime/qwenapp` уже содержит ACP, проверку структурированных ответов, политику инструментов и файлов, а также управление процессами через `processjob`. Runtime создаётся лениво: каждый поток получает собственный процесс через `startQwenThread`. `Process.Start` собирает окружение через `isolatedEnv`, но регистрирует секреты диагностики только из исходного окружения и JSON-контракта. Поэтому добавленного из файла токена в текущем списке скрываемых значений не будет.

В `process.go` есть внешние параметры `QWEN_CODE_*` и CLI-флаги ограничения инструментов. Их фактическая поддержка Nessy не доказана самим наличием этих строк в адаптере. Реальные проверки находятся в `real_cli_*_test.go` и `scripts/test-qwen-conformance.{ps1,sh}`; подмена названий не заменяет приёмку.

## Goals / Non-Goals

**Goals:**

- Отделить чтение пользовательского файла от ACP и доменного слоя; передавать runtime уже проверенный токен.
- Сделать окружение каждого дочернего процесса и его диагностику согласованными с одним снимком настроек запуска.
- Сохранить проверяемые границы текущего адаптера при смене идентичности.

**Non-Goals:**

- Универсальная система настроек, запись конфигурации, слежение за файлом и обновление токена в работающем Stepan.
- Изменение общего `agentruntime.Runtime`, форматов документов или правил ACP ради переименования.
- Миграция исторических отчётов и сохранённых значений `provider: qwen`.

## Decisions

### 1. Продолжить существующий ACP-адаптер как nessyapp

Перенести `internal/agentruntime/qwenapp` в `internal/agentruntime/nessyapp`, обновить импорты, внутренние имена, ошибки и тесты. Новый адаптер разрешает фиксированную команду `nessy` через существующий механизм PATH, включая платформенную обработку launcher-файлов. Убрать произвольный `Executable` из производственной конфигурации Nessy; тесты используют внедрение команды или временный PATH с fake-командой `nessy`.

В `parseAgentConfig` использовать уже существующий `flags.Visit`: отклонять сам факт передачи `--agent-cli-name` для Nessy, включая `nessy` и пустое значение. Для `qwen` выдавать отдельную ошибку с переходом на `--agent nessy`, до разрешения исполняемого файла. Codex и Claude сохраняют текущие настройки и override.

Альтернатива — алиас или параллельный Qwen-адаптер — противоречит согласованному удалению провайдера и оставляет два названия одного пути выполнения.

### 2. Читать настройки один раз в точке сборки

Добавить небольшой `internal/usersettings` с функцией чтения токена Nessy: домашний каталог определяется через `os.UserHomeDir`, путь строится через `filepath.Join(home, ".stepan", "settings.json")`. Для тестов отделить разбор байтов и чтение по заданному домашнему каталогу; рабочий запуск не предоставляет CLI-переопределения пути.

Разбирать ровно один JSON-документ с объектом верхнего уровня, объектом `nessy` и строкой `auth_token`. Неизвестные поля разрешены, чтобы настройки других возможностей не ломали Nessy. `null`, неверные типы, отсутствующие поля и пустые после `strings.TrimSpace` строки являются ошибками. Проверка пробельности не изменяет непустой токен: передаётся исходное строковое значение. Не интерпретировать JWT и не проверять его срок действия.

Ошибки классифицировать безопасными причинами (домашний каталог, чтение, JSON, поле, пустой токен), указывать `~/.stepan/settings.json` и `nessy.auth_token`, не включать входные байты и значения полей. Непредставимое в окружении значение с NUL также отклонять до запуска дочернего процесса как ошибку конфигурации, не печатая значение.

В `run` читать настройки только для Nessy после обычных проверок запуска, до создания сессии и запуска UI. Передать токен отдельным приватным входом фабрике runtime; не помещать его в `agentConfig`, runtime identity или сохраняемое состояние. `nessyapp.Config` получает `AuthToken`, который валидируется перед созданием runtime и перед запуском процесса для защиты прямых вызовов launcher.

Альтернатива — читать файл при создании каждого потока — даёт разные токены внутри одной сессии и переносит файловые ошибки в середину работы. Чтение из cwd или fallback на окружение противоречат спецификации. Замена файла применяется при следующем запуске Stepan.

### 3. Передавать токен только через окружение дочернего процесса

Сохранить `isolatedEnv` как единую точку сборки окружения и добавить обязательный override `NESSY_CLI_DP_AUTH_TOKEN` из `Config.AuthToken`. Сначала собрать базовое окружение, затем заменить все совпадающие ключи и получить одну итоговую запись. Сохранить существующую нормализацию регистра на Windows и чувствительность к регистру на macOS. Не вызывать `os.Setenv`: токен нужен только процессам Nessy.

Конфигурация runtime передаётся каждому `startNessyThread`, поэтому основной поток, reviewer и новые потоки получают один токен. Он не включается в argv, ACP initialize/session/prompt, JSONContract или EnvelopeSchema.

Удалить `prepareAgentLogin`, `interactiveLoginFunc`, адаптерный `RunInteractiveLogin` и их устаревшие тесты. Не добавлять другой путь авторизации: отказ Nessy с просроченным токеном остаётся безопасно диагностируемой ошибкой агента, без повторного входа или refresh.

Альтернатива — устанавливать глобальную переменную окружения — затрагивает других провайдеров и делает параллельные тесты зависимыми от глобального состояния.

### 4. Зарегистрировать токен в защите диагностики до запуска

До создания дочернего процесса добавить настроенный токен в `limitedDiagnostic.setSecrets` вместе с уже скрываемыми значениями исходного окружения и контракта. Сохранить bounded capture и редактирование перед усечением. Проверить токен без префикса `token=`, разбиение между записями stderr и границу ограничения буфера.

Сохранить `safeRuntimeError` и allowlist контекста протокольных ошибок: не выводить raw JSON-RPC message/data, окружение или Config. Проверить также путь ACP-ответа до публикации результата: если дочерний процесс вернул настроенный токен в строковых данных, остановить такой результат безопасной ошибкой до передачи в UI/документы, вместо сохранения секрета или изменения содержимого документа заменой текста. Токен не передаётся в промпты для инструкций о сокрытии.

Альтернатива — полагаться на regexp имён секретов — не скрывает голое значение нового токена. Одной защиты stderr недостаточно для требования об отсутствии токена в сохраняемых артефактах.

### 5. Разделить внутреннее переименование и внешний контракт Nessy

Внутренние имена, новые provider metadata, build tag реальных тестов и скрипты приёмки переименовать в Nessy. Обновить README, актуальные инструкции приёмки и `arch-go.yml`, если правила содержат путь старого адаптера. Исторические документы Qwen остаются свидетельствами прежней реализации.

Внешние `QWEN_CODE_*`, имена инструментов и CLI-флаги не заменять механически на выдуманные `NESSY_*`. Сохранить текущие параметры запуска как исходный контракт и проверить их на установленной целевой Nessy через справку/исходники и существующие conformance probes. Новое имя допустимо только при подтверждении поддержки. Проверки ACP, пяти разрешённых инструментов, запретов и lifecycle остаются обязательными; неподдерживаемые ограничения нельзя молча отключать. Несовместимость, требующая изменения согласованного ACP-контракта, должна быть вынесена на пересмотр плана.

Реальные тесты и оба runner-скрипта используют фиксированный `nessy` и тот же загрузчик домашней конфигурации, без аргумента токена и fallback на environment. Unit-тестам реальный токен не нужен.

## Risks / Trade-offs

- [Nessy игнорирует старые внешние параметры] → Проверить эффективное поведение инструментов и ACP реальной приёмкой; наличие флага в argv не считать доказательством ограничения.
- [Токен истекает во время работы] → Безопасная ошибка, пользователь заменяет значение и перезапускает Stepan; автоматического refresh нет.
- [Токен присутствует в памяти и окружении дочернего процесса] → Не копировать его в состояние и отчёты; это необходимое свойство выбранного контракта environment, а не хранилище секретов ОС.
- [Негативные тесты чтения файла отличаются по ОС] → Использовать внедряемое чтение для стабильной ошибки доступа и отдельные тесты реального домашнего пути.
- [Cross-build не проверяет macOS runtime] → Отдельная приёмка на физическом Apple Silicon Mac; пропуск реальных тестов не считать успехом.

## Migration Plan

1. Внести переименование и новый путь авторизации вместе, обновить fake-тесты, документацию и runners.
2. Пользователь вручную создаёт `~/.stepan/settings.json` по примеру спецификации и меняет запуск на `stepan --agent nessy`; старые параметры отклоняются с подсказкой.
3. Выполнить Go-тесты и сборки, затем opt-in приёмку Nessy на Windows/amd64 и физическом Apple Silicon Mac. Зафиксировать версию CLI и результаты без токена. Не объявлять непроведённую runtime-приёмку выполненной.
4. При необходимости отката вернуть предыдущую версию Stepan и прежнюю команду запуска. Домашний файл не удалять и не переписывать автоматически; историческое состояние не мигрируется в этом изменении.
