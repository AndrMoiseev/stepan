# SDD framework: pre-development flow

Статус: **черновик для обсуждения**

Этот документ фиксирует только часть workflow до начала реализации. Он описывает
роли, переходы, ревью, участие пользователя, размещение артефактов и минимальные
форматы служебных файлов.

## 1. Результат flow

Flow превращает явно заданную пользователем идею в утверждённый пакет
спецификации:

```text
idea → requirements → design → plan → ready for implementation
```

Пакет состоит из четырёх логических артефактов:

- `idea` — какую проблему решаем, зачем и для кого;
- `requirements` — проверяемые требования и границы;
- `design` — техническое решение;
- `plan` — порядок реализации и проверки.

Эти артефакты хранятся внутри `.stepan/specs/<spec-id>/`.

## 2. Принципы

1. Flow запускается только по явному запросу пользователя. Роутер не угадывает,
   хочет ли пользователь начать или продолжить разработку.
2. Артефакты и состояние в репозитории являются источником истины. История чата
   не требуется для продолжения работы.
3. Проектные входы отделены от артефактов конкретного изменения и объявляются
   отдельно для каждой роли в конфигурации project adapter.
4. Каждая содержательная роль запускается новым агентом с чистым контекстом.
5. Модель и reasoning effort роли задаются конфигурацией проекта, а не выбираются
   заново для каждой задачи.
6. Агент задаёт вопрос только тогда, когда без решения пользователя нельзя
   получить корректный артефакт. Обязательные пользовательские checkpoints не
   считаются уточняющими вопросами.
7. Утверждённый артефакт нельзя молча изменить на следующей стадии.
8. Канонические артефакты не содержат provider-, model- и thread-specific
   metadata.

## 3. Роли

### Router

Управляет переходами и состоянием, запускает роли, сохраняет их результаты и
показывает пользователю checkpoints. Не принимает продуктовые и технические
решения за авторов или пользователя. Только router изменяет `state.yaml` и
сохраняет структурированные результаты reviewer в `review/*.yaml`.

### Framer

Формирует `idea` из исходного запроса пользователя. Описывает проблему, цель,
целевого пользователя, ожидаемый эффект и явные границы.

### Specifier

Создаёт `requirements` по утверждённой идее и постоянным фактам проекта.
Формулирует проверяемые требования, предпочтительно в EARS-подобной форме со
стабильными идентификаторами.

### Designer

Создаёт `design` по утверждённым идее и требованиям. Описывает выбранное решение,
затрагиваемые компоненты, ограничения, риски и способы проверки реализуемости.

### Planner

Создаёт `plan` по утверждённым идее, требованиям и дизайну. Не перепроектирует
решение. Разбивает его на упорядоченные, проверяемые шаги и связывает шаги с
требованиями.

### Spec reviewer

Независимо проверяет pre-development артефакты. Работает в read-only режиме,
не редактирует проверяемые документы и не подменяет пользователя. Для каждого
ревью запускается новый агент. Reviewer возвращает результат router и не пишет
даже собственный review-файл.

`Code reviewer` является отдельной будущей ролью и в этот flow не входит.

`Framer`, `specifier`, `designer` и `planner` напрямую записывают только
принадлежащий роли артефакт. После запуска роли router проверяет фактическую
границу изменений.

## 4. Основной flow

```text
start
  → draft idea
  → user checkpoint: idea
  → draft requirements
  → agent review: requirements
  → user checkpoint: requirements
  → draft design
  → agent review: design
  → user checkpoint: design
  → draft plan
  → agent review: complete package
  → user checkpoint: plan
  → ready for implementation
```

### 4.1 Idea

1. Пользователь явно начинает новое изменение и передаёт исходную идею.
2. Router генерирует `spec-id`, создаёт каталог изменения и начальный
   `state.yaml` до запуска содержательной роли.
3. Router запускает `framer` в чистом контексте.
4. Если без дополнительного решения нельзя сформулировать содержательную идею,
   `framer` возвращает минимальный блокирующий вопрос.
5. После создания `idea` flow переходит в пользовательский checkpoint.

Отдельное агентное ревью идеи не выполняется: намерение и ценность определяет
пользователь.

### 4.2 Requirements

1. Router запускает нового `specifier` и передаёт ему постоянные факты проекта и
   утверждённую `idea`.
2. `Specifier` создаёт `requirements` либо возвращает блокирующий вопрос.
3. Новый `spec reviewer` читает `idea` и `requirements`.
4. Исправимые blocking findings возвращаются новому экземпляру `specifier`.
5. После исправления выполняется новое независимое ревью.
6. Если для устранения finding требуется решение пользователя, flow
   останавливается и показывает это решение пользователю.
7. После успешного ревью flow переходит в пользовательский checkpoint.

Ревью проверяет полноту, непротиворечивость, однозначность, проверяемость,
границы, исключения и соответствие исходной идее.

### 4.3 Design

1. Router запускает нового `designer` и передаёт ему постоянные факты проекта,
   утверждённые `idea` и `requirements`.
2. `Designer` создаёт `design` либо возвращает блокирующий вопрос.
3. Новый `spec reviewer` читает `idea`, `requirements` и `design`.
4. Исправимые blocking findings проходят цикл исправления и повторного ревью.
5. После успешного ревью flow переходит в пользовательский checkpoint.

Ревью проверяет покрытие требований, совместимость с ограничениями проекта,
реализуемость, явно принятые компромиссы, риски и отсутствие необоснованной
сложности.

### 4.4 Plan

1. Router запускает нового `planner` и передаёт ему постоянные факты проекта и
   все утверждённые артефакты.
2. `Planner` создаёт `plan` либо возвращает блокирующий вопрос.
3. Новый `spec reviewer` выполняет комплексное ревью всего пакета.
4. Исправимые blocking findings возвращаются автору соответствующего артефакта,
   после чего зависимые артефакты пересматриваются.
5. После успешного ревью flow переходит в финальный пользовательский checkpoint.
6. Утверждение плана переводит изменение в `ready for implementation`.

Финальное ревью проверяет сквозную трассируемость:

```text
problem → requirements → design decisions → plan steps
```

Каждое требование должно быть покрыто дизайном и хотя бы одним проверяемым шагом
плана. План не должен содержать скрытых технических решений, отсутствующих в
утверждённом дизайне.

## 5. Агентное ревью

Для каждой стадии хранится только последнее актуальное ревью:

```text
review/
├── requirements.yaml
├── design.yaml
└── plan.yaml
```

Повторное ревью перезаписывает файл своей стадии. Устранённые findings исчезают
из актуального снимка; неустранённые сохраняют прежние IDs.

Все review-файлы используют одну схему. Например, `review/design.yaml`:

```yaml
schema_version: 1
stage: design

inputs:
  idea.md: sha256:...
  requirements.md: sha256:...
  design.md: sha256:...

verdict: pass | changes-required

findings:
  - id: DES-R-001
    severity: blocking | advisory
    references:
      - DES-003
      - REQ-007
    problem: "..."
    recommendation: "..."
```

- `inputs` содержит hashes всех прочитанных артефактов; `review/plan.yaml`
  связывается со всеми четырьмя файлами пакета;
- `blocking` означает, что пакет пока нельзя рекомендовать пользователю для
  утверждения;
- `advisory` показывается пользователю, но не блокирует checkpoint;
- `pass` может содержать advisory findings, но не blocking findings;
- каждый finding имеет стабильный ID и ссылается на конкретные разделы или IDs;
- стилистические предпочтения без влияния на корректность не являются finding;
- ревьюер не редактирует исходные артефакты.

После первоначального ревью допускаются не более трёх полных автоматических
циклов `revision → review` для одной стадии. Первоначальное ревью в лимит не
входит. После третьего `changes-required` router переводит flow в
`awaiting-decision` и показывает пользователю оставшиеся findings; четвёртый
цикл автоматически не запускается. Счётчик хранится в `state.yaml` и
сбрасывается при переходе к другой стадии либо после нового решения пользователя.

## 6. Пользовательский checkpoint

Пользователь получает checkpoint только после создания артефакта и завершения
предусмотренного для него агентного ревью.

Доступные действия:

- `continue` — явно утвердить текущий артефакт и перейти к следующей стадии;
- `continue-and-commit` — утвердить артефакт и создать ограниченный Git commit;
- `revise <feedback>` — передать замечания новому экземпляру роли-автора;
- `question <text>` — получить ответ без изменения артефакта и состояния;
- `accept-risk` — явно принять перечисленные blocking findings;
- `stop` — завершить текущую сессию без запуска следующей стадии.

Обычный `continue` доступен только после `verdict: pass`. При
`changes-required` требуется revision либо отдельный `accept-risk` с IDs
принятых findings. Комментарий к принятому риску опционален.

После `revise` обновлённый артефакт заново проходит предусмотренное для него
агентное ревью, прежде чем вернуться в пользовательский checkpoint.

`stop` не требует отдельного состояния `paused`: checkpoint уже сохранён и
может ждать пользователя неограниченное время. В другой сессии пользователь
явно указывает идентификатор изменения и просит продолжить его. Router читает
состояние и повторно показывает ожидающий решения checkpoint.

Молчание, завершение сессии и отсутствие возражений не являются утверждением.

`continue-and-commit` не является настройкой на весь flow: пользователь явно
выбирает его на конкретном checkpoint. Commit включает только
`.stepan/specs/<spec-id>/` и использует сообщение
`sdd(<spec-id>): approve <stage>`. Остальные изменения рабочей копии не
добавляются в commit.

Перед commit router повторно сверяет hashes, состав файлов и Git snapshot
каталога спецификации. Неожиданное изменение останавливает операцию в
`awaiting-decision`; router ничего не добавляет в index и предлагает считать
изменение revision либо остановиться.

Approval и commit считаются одной checkpoint-операцией: следующая стадия не
запускается, пока commit не создан и не проверен. При ошибке Git checkpoint
остаётся в `awaiting-approval`, а пользователь может повторить
`continue-and-commit`, выбрать обычный `continue`, revision или stop. Router
убирает только созданные им временные данные и изменения index; пользовательские
или hook-created файлы не откатываются. Если после ошибки появились
неожиданные изменения, flow вместо этого переходит в `awaiting-decision`.

## 7. Утверждение и возврат на предыдущую стадию

`continue` фиксирует текущую версию артефакта как утверждённую baseline.
Approval связывается с SHA-256 артефакта и, если оно предусмотрено стадией,
SHA-256 актуального review-файла. Для `idea.md` сохраняется только hash
артефакта. Принятые риски сохраняются внутри соответствующего approval.

Перед вычислением hash каждый Markdown- или YAML-файл декодируется как валидный
UTF-8, один начальный BOM удаляется, `CRLF` и одиночный `CR` заменяются на `LF`,
а в конце оставляется ровно один `LF`. Остальные code points и whitespace,
включая значимые для Markdown trailing spaces, сохраняются; Unicode normalization
не выполняется. SHA-256 вычисляется по получившимся UTF-8 bytes. Следующие роли
используют утверждённые артефакты как read-only вход.

Если поздняя стадия обнаружила материальную проблему в утверждённом артефакте:

1. flow возвращается к стадии-владельцу артефакта;
2. пользователь видит причину возврата;
3. изменение артефакта удаляет из `state.yaml` approvals всех зависимых
   последующих артефактов;
4. изменённый артефакт снова проходит агентное ревью и пользовательский
   checkpoint;
5. существующие downstream-файлы и reviews сохраняются, но считаются stale по
   несовпавшим hashes;
6. роли точечно обновляют stale-артефакты, после чего они проходят новое ревью.

Пользователь может явно принять известный риск и продолжить вопреки finding.
Такое решение должно быть сохранено вместе с состоянием изменения.

Если router обнаружил ручное изменение утверждённого артефакта, он не принимает
и не откатывает его автоматически. Пользователь должен явно решить, считать ли
изменение revision.

## 8. Контекст и handoff ролей

Каждый запуск роли получает только:

- собственный role prompt;
- идентификатор изменения;
- project inputs, объявленные конфигурацией конкретной роли;
- явно перечисленные входные артефакты;
- замечания последнего ревью, если выполняется revision;
- ожидаемый результат и разрешённую область записи.

История родительского диалога и разговор предыдущего агента не передаются.
Handoff выполняется через сохранённые артефакты. Reviewer не получает рассуждения
автора и оценивает только доступные факты и документы.

Agent-, model-, provider- и thread IDs не записываются в `state.yaml` и review.
После прерывания роль запускается заново по сохранённым файлам.

Version-controlled спецификация не ссылается на ignored runtime-данные
`.stepan/runs/**`. `design.md` и `plan.md` могут ссылаться на version-controlled
код и конфигурацию. Все пути записываются относительно корня репозитория с `/`
как разделителем.

## 9. Логические состояния

Состояние хранится как независимые поля `stage` и `status`.

- `stage`: `idea`, `requirements`, `design`, `plan`;
- `status`: `drafting`, `reviewing`, `revising`, `awaiting-approval`,
  `awaiting-decision`, `approved`.

После утверждения плана состояние равно `stage: plan`, `status: approved`.
Готовность к реализации выводится из этой пары; отдельные `paused` и
`ready-for-implementation` не нужны.

Минимальный `state.yaml`:

```yaml
schema_version: 1
created_at: 2026-08-15T12:00:00Z
stage: design
status: awaiting-approval
automatic_revision_attempts: 0

approvals:
  idea:
    artifact_sha256: sha256:...
  requirements:
    artifact_sha256: sha256:...
    review_sha256: sha256:...
    accepted_risks: []

pending: null
```

`created_at` неизменяем, записывается в UTC/RFC 3339 и задаёт порядок
спецификаций вместе с `spec-id`: `(created_at, spec-id)`. Общий index-файл не
используется.

Начальный файл создаётся сразу после выбора `spec-id` со значениями
`stage: idea`, `status: drafting`, `automatic_revision_attempts: 0`, пустыми
`approvals` и `pending: null`. Счётчик относится только к текущей стадии и
сохраняется между сессиями.

Незавершённый блокирующий вопрос или revision feedback хранится одним объектом:

```yaml
pending:
  kind: clarification | revision
  stage: design
  request: "..."
  response: null
```

Ответ пользователя записывается в `response` до запуска новой роли. `pending`
удаляется только после успешной обработки. История переходов, timestamps
обновления и IDs агентных сессий в `state.yaml` не хранятся.

Каждый `state.yaml` и review-файл содержит собственный целочисленный
`schema_version`. Версия увеличивается только при несовместимом изменении формы
или смысла; добавление игнорируемого optional-поля её не меняет. Reader применяет
последовательные, детерминированные миграции старых поддерживаемых версий в
памяти. Файл записывается в текущей версии только при следующем обычном изменении
router; review обновляется только новым ревью. Поэтому schema upgrade сам по
себе не меняет approval hashes. Отдельной массовой миграции нет. Неизвестная
будущая версия или миграция с потерей смысла останавливает flow без записи и
требует явного обновления инструмента либо ручного решения.

## 10. Переносимость и Codex

Канонический flow, роли и артефакты не должны зависеть от Codex. Интеграция с
конкретной агентной системой является тонким adapter layer.

Для Codex предполагается:

- один skill-router, содержащий только правила маршрутизации и checkpoints;
- project-scoped custom agents для содержательных ролей;
- role-specific model, reasoning effort и sandbox в конфигурации проекта;
- отдельные subagent threads с минимально необходимым входным контекстом;
- хранение durable state в репозитории, а не в Codex thread.

Официальная документация OpenAI подтверждает, что skills предназначены для
повторяемых workflow, а project-scoped custom agents могут иметь собственные
инструкции, модель и sandbox: [Build skills](https://learn.chatgpt.com/docs/build-skills),
[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Конкретный Codex adapter будет проверен отдельно до признания framework
реализуемым.

Codex adapter первой версии поставляется как repository overlay, а не plugin:

```text
.agents/skills/sdd/
├── SKILL.md
├── scripts/
│   └── sdd.py
└── references/
    ├── protocol.md
    ├── roles/
    │   ├── framer.md
    │   ├── specifier.md
    │   ├── designer.md
    │   ├── planner.md
    │   └── spec-reviewer.md
    └── schemas/
        ├── state-v1.json
        └── review-v1.json
.codex/
├── config.toml
└── agents/
    ├── framer.toml
    ├── specifier.toml
    ├── designer.toml
    ├── planner.toml
    └── spec-reviewer.toml
```

`references/**` содержит provider-neutral protocol, prompts и schemas.
`scripts/sdd.py` использует только Python 3 standard library, детерминированно
генерирует `spec-id` и canonical hashes и не изменяет состояние flow. `SKILL.md`
содержит только Codex-маршрутизацию и checkpoints. Agent TOML-файлы являются
тонкими wrappers: выбирают role prompt, project inputs, model, reasoning effort
и sandbox; общие ограничения агентов находятся в `.codex/config.toml`.

Plugin не используется в первой версии, поскольку документированный plugin
manifest упаковывает skills, hooks и MCP, но не project-scoped agents и project
config. Если эти возможности появятся либо понадобится распространение только
skill-части, overlay можно дополнительно завернуть в plugin без изменения
portable protocol: [Package your plugin](https://developers.openai.com/plugins/build/plugins),
[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

До реализации adapter должен пройти минимальный набор forward-tests:

1. **Чистый контекст.** Parent и предыдущая роль получают разные canary-строки,
   отсутствующие в разрешённых inputs. Новая роль не должна видеть их; записанный
   launch envelope должен содержать только явно перечисленные файлы и prompt.
2. **Write boundaries.** Автору предлагается изменить свой артефакт и sentinel
   вне разрешённой области, reviewer — любой файл. Snapshot после запуска должен
   содержать только разрешённое изменение автора и ни одного изменения reviewer;
   router обязан отвергнуть нарушающий результат до перехода состояния.
3. **Resume.** Процесс принудительно завершается после каждой durable-записи и во
   время каждой роли. Новая host-сессия только по файлам репозитория должна
   показать тот же следующий checkpoint; итоговые артефакты и hashes должны
   совпасть с непрерывным контрольным проходом.
4. **Переносимость.** Один набор golden scenarios выполняется через fake runner и
   Codex adapter. Переносимость на другие системы считается подтверждённой только
   после прохождения того же набора вторым реальным adapter; fake runner этого не
   доказывает и не является причиной заранее вводить общий runtime interface.

## 11. Хранение изменений

Portable protocol не задаёт общий набор project inputs. Источники фактов и
правила их поиска объявляются отдельно для каждой роли в project-scoped agent
configuration. Роль загружает их только при запуске своего шага; router не
читает их заранее.

Артефакты конкретного изменения хранятся отдельно:

```text
.stepan/specs/<spec-id>/
├── state.yaml
├── idea.md
├── requirements.md
├── design.md
├── plan.md
└── review/
    ├── requirements.yaml
    ├── design.yaml
    └── plan.yaml
```

`.stepan/specs/**` является version-controlled частью репозитория. Остальные
подкаталоги `../..` предназначены для локальных runtime-данных, логов,
временных файлов и evidence и не добавляются в Git.

Артефакты в `.stepan/specs/<spec-id>/` описывают предполагаемое изменение и
состояние его подготовки. Обновление постоянных project facts относится к
будущему post-development flow и находится вне этого документа.
`.stepan/specs/<spec-id>/` остаётся version-controlled историческим пакетом и не
перемещается в отдельный архив. Ignored runtime-данные `.stepan/runs/**` не
являются частью пакета и очищаются отдельной локальной retention policy.
`created_at` служит только для порядка спецификаций и не управляет синхронизацией.

Основные артефакты являются чистым Markdown без YAML frontmatter. Требования,
значимые design decisions и шаги плана получают стабильные IDs `REQ-*`,
`DES-*` и `STEP-*`. После первого присвоения IDs не перенумеровываются;
пропуски допустимы.

Файлы стадий и reviews создаются лениво, без пустых placeholders.

`Spec-id` генерируется автоматически из идеи скриптом
`../../../.agents/skills/sdd/scripts/sdd.py` и показывается пользователю.
Нормализация первой версии:

1. строка переводится в lowercase;
2. русские буквы транслитерируются фиксированной таблицей
   `а=a, б=b, в=v, г=g, д=d, е=e, ё=yo, ж=zh, з=z, и=i, й=y, к=k, л=l, м=m,
   н=n, о=o, п=p, р=r, с=s, т=t, у=u, ф=f, х=kh, ц=ts, ч=ch, ш=sh, щ=shch,
   ъ="", ы=y, ь="", э=e, ю=yu, я=ya`;
3. любая последовательность остальных символов вне `[a-z0-9]` заменяется одним
   `-`, крайние `-` удаляются;
4. пустой результат заменяется на `change`, полная длина ограничивается 63
   символами, крайний обрезанный `-` удаляется;
5. при конфликте router предлагает продолжить существующее изменение либо
   создать новое с наименьшим свободным суффиксом `-2`, `-3`, ...; перед
   добавлением суффикса base обрезается так, чтобы итог сохранил лимит 63.

## 12. Content contracts артефактов

Все обязательные разделы непустые. Дополнительные разделы допустимы, если они
добавляют информацию, а не placeholders.

### 12.1 `idea.md`

Обязательная структура:

```text
# Idea
## Problem
## Goal
## Target user
## Expected outcome
## Scope
### In
### Out
```

`Problem` описывает наблюдаемую проблему, `Goal` — желаемое изменение,
`Expected outcome` — проверяемый эффект. `Scope` явно отделяет включённое от
исключённого.

### 12.2 `requirements.md`

Обязательная структура:

```text
# Requirements
## Requirements
### REQ-001 — <short name>
Statement: <one EARS-like requirement>
Verification: <observable check>
## Boundaries and assumptions
```

Каждый requirement содержит одну атомарную обязанность и использует наиболее
короткую подходящую форму:

```text
[Where <feature>,] [While <state>,]
[When <trigger>, | If <undesired condition>,]
the <system> shall [not] <observable response>.
```

Квадратные блоки опциональны; из альтернатив `When` и `If` выбирается не более
одной. Независимые обязанности не соединяются `and/or`, а получают разные IDs.
`Verification` описывает наблюдение или проверку, но не навязывает реализацию.

### 12.3 `design.md`

Обязательная структура:

```text
# Design
## Overview
## Decisions
### DES-001 — <short name>
Covers: REQ-001, ...
Decision: <chosen solution>
Rationale: <why this solution>
## Affected components
## Constraints, risks and trade-offs
## Verification
```

Каждый `REQ-*` покрывается хотя бы одним `DES-*`. Существенная альтернатива
упоминается только если объясняет выбранный компромисс. `Verification` описывает,
как до реализации проверить осуществимость решения и после неё — соответствие
дизайну.

### 12.4 `plan.md`

Обязательная структура:

```text
# Plan
## Steps
### STEP-001 — <short name>
Covers: REQ-001, DES-001, ...
Outcome: <one verifiable result>
Changes: <expected components or paths>
Verification: <command or observable check>
## Final verification
```

Порядок `STEP-*` задаёт порядок исполнения. Каждый `REQ-*` и `DES-*` покрывается
хотя бы одним шагом; один шаг имеет один проверяемый outcome. `Final verification`
проверяет пакет целиком и межшаговые эффекты.

## 13. Явно вне текущего scope

- правила стадий после `stage: plan`, `status: approved`;
- реализация adapters для Codex и других агентных систем до завершения
