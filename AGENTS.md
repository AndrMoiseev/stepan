# AGENTS.md

## Правила Go по задаче

Перед разработкой или ревью Go-кода прочитайте [индекс правил](docs/development/go/index.md) и загрузите применимые темы по задаче и затронутому поведению. При расширении области изменений повторите выбор. Документы с правилами общие для разработки и ревью.

## Глубокие модули и вложенные пакеты

При проектировании нового модуля стремитесь к небольшому интерфейсу, скрывающему связное поведение. Модуль, обслуживающий один flow, по умолчанию размещайте внутри его каталога; место уточняйте по фактическим потребителям и направлению зависимостей. В названии вложенного пакета обозначайте роль без повторения имени родителя. Если вложенный пакет нужен хранилищу или точке сборки, зависимость направляйте на этот пакет, а не на пакет flow. Правила импортов обновляйте в `arch-go.yml`.

## Сборка и тесты

Требуется Go 1.26.5. Все команды запускаются из корня репозитория.

Поддерживаемая сборка для Windows/amd64:

```powershell
go build -o stepan.exe ./cmd/stepan
go test ./...
```

Нативная сборка на Apple Silicon Mac:

```sh
go build -o stepan ./cmd/stepan
go test ./...
```

Кросс-сборка для macOS на Apple Silicon:

```powershell
$env:GOOS = "darwin"
$env:GOARCH = "arm64"
$env:CGO_ENABLED = "0"
go build -o stepan-darwin-arm64 ./cmd/stepan
Remove-Item Env:GOOS, Env:GOARCH, Env:CGO_ENABLED
```

Cross-build проверяет только компиляцию. Runtime-приёмку macOS выполняйте на
физическом Apple Silicon Mac по
`docs/changes/features/macos-compatibility/manual-test-plan.md`. Intel Mac, signing и
notarization пока не поддерживаются.

Для запуска тестов отдельного пакета используйте `go test ./путь/к/пакету`, например `go test ./internal/specflow`.

## Наборы тестов

В `internal/flows/impl_loop` обращайтесь к Git только через модуль
[`workspace`](internal/flows/impl_loop/workspace/README.md), включая создание
и наблюдение коммитов. Git CLI и операции `internal/git` разрешены внутри
`workspace/git`; вне него разрешены только общие типы снимков, различий и ошибок.
Тесты оркестрации используют `workspace/testfs` или специализированный fake.
Настоящий Git оставляйте для контрактов адаптера и интеграционных сценариев
hooks/индекса с тегом `git_integration`; их Git-fixtures находятся внутри
`workspace/git`. Границу проверяет `TestImplementationGitAccessGoesThroughWorkspace`.
При изменении поведения адаптеров обновляйте общий `TestWorkspaceConformance`.

Обычный запуск выполняет только быстрые изолированные тесты и не должен
запускать внешние процессы:

```powershell
go test ./...
```

Контракты с настоящим Git запускаются отдельно:

```powershell
go test -count=1 -parallel=4 -tags=git_integration ./...
```

Тесты управления дочерними процессами и fake CLI запускаются отдельно:

```powershell
go test -count=1 -tags=process_integration ./...
```

Полная локальная проверка выполняет оба интеграционных набора:

```powershell
make test-all
```

Без Make используйте `go run ./internal/testall`. Запускатель ограничивает весь
`go test` 120 секундами, включая сборку тестов, и завершает его дерево процессов
при таймауте. Сборка самого запускателя предшествует этому отсчёту.
Флаг `go test -timeout` сам по себе ограничивает пакет, а не полный прогон.

При неожиданном таймауте тестов **остановите работу над задачей** после завершения
принадлежащих прогону процессов. Сообщите пользователю команду, лимит и последний
вывод; предложите пересмотреть архитектуру модулей и тестовых границ.
Продолжайте только после решения пользователя. Не увеличивайте лимит,
не перезапускайте и не дробите набор для обхода таймаута автоматически.
Ожидаемый таймаут внутри успешно проходящего теста механизма отмены не является
таймаутом прогона и не требует остановки работы.

Для интеграционных наборов сохраняйте `-count=1`: обработка большого журнала
файловых обращений для кеша результатов Go может надолго задерживать завершение
команды после тестов. Кеш сборки этот флаг сохраняет.

Файлы тестов, импортирующие `os/exec`, обязаны иметь build tag
`git_integration`, `process_integration` или специальный ручной tag вроде
`nessy_real_cli`. Это правило проверяется архитектурным тестом.

## Codex App Server: response schema

Для `turn/start` schema в `text.format.schema` используйте flat object-schema:

- `oneOf` не поддерживается;
- `required` должен содержать каждый ключ из `properties`;
- для семантически необязательного поля используйте required transport-placeholder
  и нормализуйте его до передачи в доменный слой. Например, intent `draft`
  передаёт `"message": ""`; пустое значение не является сообщением draft.
